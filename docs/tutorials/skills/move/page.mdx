# Move to a pose

Opening the gripper was one number. Moving the arm to "home" is six numbers with a name. That name is a skill's vocabulary, so it lives in the skill's config, not on the arm. The arm still just receives joint targets. {{ className: 'lead' }}

## Install the skill

```bash
solarian install move-skill
```

This installs `solarian-move-skill` and copies `conf/skills/move.yaml` the first time. Open that file. It already has a `home` pose and a `ground` pose, both in the normalized −100 to 100 joint range, plus a gripper width in millimetres. Those numbers are a reasonable tuck for this arm. You will add one pose of your own in a moment.

Each pose is keyed by module name, and the template names them `right_arm` and `right_gripper`. Rename those keys to `arm` and `gripper` in both poses. A pose whose keys match no module moves nothing, and no error says so.

`MoveSkill` reads `poses[name]`, sends one `MOVE_J`, and finishes when a timeout elapses. The module drives the path. The skill does not interpolate.

`MOVE_J` is `ArmModule`'s joint move. The arm from Tutorial 2 answers `MOVE_ARM` and replaces `control_step`, so this skill does not reach those servos until the kinematics section removes both. The gripper module already handles `MOVE_J`.

## A key for home

`my_robot/controller.py`:

```python
from solarian.core import Controller
from solarian.core.event import Event, EventType, event_handler
from solarian_move_skill import MoveSkill

from my_robot.skills import OpenGripperSkill


class MyRobotController(Controller):
    skills = (OpenGripperSkill, MoveSkill)

    @event_handler(EventType.KEY_DOWN)
    def on_key_down(self, event: Event):
        key = event.data["key"]
        if key == "o":
            self.start_skill(OpenGripperSkill(params={"gripper": "gripper"}))
        elif key == "0":
            self.start_skill(MoveSkill(params={
                "pose": "home",
                "arm": "arm",
                "gripper": "gripper",
            }))
```

The handler is in place. Leave `0` unpressed until the kinematics model is on the arm: a `MOVE_J` with no joint limits raises inside the arm module. Press `o` to see a skill run; that one only commands the gripper. Pressing a key starts the skill again. It does not toggle.

## Name your own pose

In `conf/skills/move.yaml`, under `poses:`, add a pose you can recognize. These values are mid-travel on the shoulder and a bent elbow, so the hand sits out in front instead of tucked:

```yaml
    reach:
        arm:
            shoulder_pan: 0.0
            shoulder_lift: 20.0
            elbow_flex: 40.0
            wrist_flex: -20.0
            wrist_yaw: 0.0
            wrist_roll: 0.0
        gripper:
            gripper: 40.0
```

Add a key:

```python
elif key == "1":
    self.start_skill(MoveSkill(params={
        "pose": "reach",
        "arm": "arm",
        "gripper": "gripper",
    }))
```

Restart the controller so it loads the new key. If `1` raises `KeyError` naming `reach`, the YAML key and the string in `params` disagree, or the controller was started from a directory that is not the project root. The arm still waits for the kinematics model.

## Inverse kinematics

Joint poses were enough for `home` and `reach`. A policy does not speak in joint angles. It speaks in where the fingertips should be: `x, y, z` and three rotations. Inverse kinematics is the arm module turning that into joints.

Replace `my_robot/modules/my_arm_module.py`. `MyActions`, `_handle_move_arm`, and `control_step` have to go. `control_step` is what the loop calls, and `ArmModule`'s version is what samples a `MOVE_J` and writes the servos. Cartesian commands use the same model. The joint limits come from the kinematics backend, which is why this takes over now and not in Tutorial 2.

```python
from solarian.core.arm_module import ArmModule
from solarian.core.ik import CartesianIKActuator, MinkIK
from solarian_feetech.actuator import FeetechServo

JOINTS = [
    "shoulder_pan",
    "shoulder_lift",
    "elbow_flex",
    "wrist_flex",
    "wrist_yaw",
    "wrist_roll",
]


class MyArmModule(ArmModule):
    shoulder_pan = FeetechServo(model="sts3250")
    shoulder_lift = FeetechServo(model="sts3250")
    elbow_flex = FeetechServo(model="sts3250")
    wrist_flex = FeetechServo(model="sts3250")
    wrist_yaw = FeetechServo(model="sts3215")
    wrist_roll = FeetechServo(model="sts3215")

    x = CartesianIKActuator()
    y = CartesianIKActuator()
    z = CartesianIKActuator()
    rx = CartesianIKActuator()
    ry = CartesianIKActuator()
    rz = CartesianIKActuator()

    # The arm MJCF, not the scene. Joint names here are unprefixed.
    # sim_joint in the YAML stays prefixed, because that is the composed world.
    ik_backend = MinkIK(
        mjcf="assets/arm1/arm1.xml",
        joints=dict(zip(JOINTS, JOINTS)),
        frame="flange",
        position_cost=1.0,
        orientation_cost=1.0,
    )
```

The six `CartesianIKActuator`s are the pose. `frame="flange"` is the wrist site in the arm model. The fingertips are not the flange. They sit a fixed offset beyond it, which the gripper module already measured. Pass that offset when you construct the arm, in `my_robot/robot.py`:

```python
arm = MyArmModule(ik_tcp=Gripper1FeetechModule.tcp_from_flange)
```

In `conf/modules/arm.yaml`, the module has to interpolate poses, not just hold a position. Add, next to `frequency`:

```yaml
interpolator_type: pose
max_speed: [0.25, 0.6]    # metres/second, radians/second
max_accel: [0.5, 3.0]
```

And the action schema has to grow the six axes, or a Cartesian command has nowhere to land. In `MyArmAction`:

```python
x = ActuatorField(MyRobotRobot.arm.x.pos)
y = ActuatorField(MyRobotRobot.arm.y.pos)
z = ActuatorField(MyRobotRobot.arm.z.pos)
rx = ActuatorField(MyRobotRobot.arm.rx.pos)
ry = ActuatorField(MyRobotRobot.arm.ry.pos)
rz = ActuatorField(MyRobotRobot.arm.rz.pos)
```

Do the same six lines on `MyArmObs`, with `SensorField`. The observation is how anything, including you in a log, reads the pose the kinematics produced.

Restart the robot and the controller. Press `0`. The arm should fold toward the tucked pose in `move.yaml`, and the gripper should open to the width in that pose. Press `1` and the arm reaches. Both poses are joint targets, and `ArmModule` handles `MOVE_J` itself. If the arm stays, `_handle_move_arm` or `control_step` is still on the class. If nothing moves and nothing fails, the pose's keys still say `right_arm`.

The contract you just implemented is the one in [Adding a new arm](/docs/ik#adding-a-new-arm): joint servos, six Cartesian actuators, a `MinkIK` backend, and `interpolator_type: pose`. The reference has the rest of the fields. You have enough for a policy to ask for a hand pose.
