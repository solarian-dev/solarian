# Kinematics

The motors speak joint coordinates. The task speaks hand poses. **Kinematics** is the conversion between the two, using only the shape of the arm: its link lengths and joint axes. {{ className: 'lead' }}

## Two directions

<KinematicsFigure />

The figure is the two-link arm from the [previous chapter](/docs/tutorials/gentle-intro/configuration). The card at the top shows what goes in and what comes out. Pin **Forward** or **Inverse** to stay on one beat.

**Forward kinematics** (FK) takes the joint angles and returns the hand pose. Walk out along the chain: the first link leaves the base at q₁, the second leaves the elbow at q₂ more, and the end of the second link is the hand. One set of angles always gives exactly one pose.

**Inverse kinematics** (IK) goes the other way. It takes a hand pose and returns joint angles that put the hand there. It answers the question a task actually asks: *which way do I turn each motor to reach that cup?*

## When you use each

Use **forward kinematics** when the joints are known and you want the hand:

- the hand pose in a recording, computed from the measured joints;
- where a camera on the wrist is looking from;
- drawing the robot in a simulator or a 3D view.

Use **inverse kinematics** when the goal is a place in the world:

- a skill that says "go to this pose";
- teleoperation that moves the hand in a straight line;
- a learned policy that outputs hand motion, as the one in this course does.

## Two answers, or none

Forward kinematics is a formula. Inverse kinematics is a search, and the figure's **Inverse** beat shows why that search can surprise you.

**More than one answer.** The faded arm reaches the same target with the elbow bent the other way. Both are correct. A six-joint arm can have several such folds for one pose, and the solver has to pick one, usually the one closest to where the arm already is.

**No answer.** A target past the reach of the stretched arm has no solution at all. Neither does a target the joint limits keep the arm from turning toward.

## The workspace

The **workspace** is every position the hand can reach. Pin **Workspace** to see it as a cloud. The link lengths set its outer edge, which is the arm stretched out. Joint limits carve pieces away from there.

A target inside the cloud can still be out of reach at the orientation you ask for. Position and orientation share the same six joints, so a far reach usually leaves the wrist fewer ways to turn. For the SO-106, the workspace is a region around its base roughly as big as the arm itself.

## In Solarian

Solarian computes inverse kinematics with `MinkIK`, a solver that reads the arm's MuJoCo model file. The link lengths, joint axes, and joint limits live in that file, so the solver and the simulator always agree on the arm's shape. The solver takes small steps from the arm's current joints toward the target, which keeps it on the fold the arm is already in.

In [Tutorial 3](/docs/tutorials/skills/move) you add it to the arm module, next to the six task-coordinate actuators:

```python {{ title: 'so106/modules/right_arm.py' }}
from solarian.core.arm_module import ArmModule
from solarian.core.ik import CartesianIKActuator, MinkIK
from solarian_feetech.actuator import FeetechServo

JOINTS = [
    "shoulder_pan",
    "shoulder_lift",
    "elbow_flex",
    "wrist_flex",
    "wrist_yaw",
    "wrist_roll",
]


class RightArmModule(ArmModule):
    # ... the six FeetechServo joints and six CartesianIKActuator axes ...

    ik_backend = MinkIK(
        mjcf="assets/so106/so106.xml",
        joints=dict(zip(JOINTS, JOINTS)),
        frame="flange",
        position_cost=1.0,
        orientation_cost=1.0,
    )
```

`frame="flange"` is the frame the solver aims: the mounting plate at the end of the wrist. The fingertips sit a fixed distance past it. That offset is the tool frame from the previous chapter, and the gripper module already knows it, so the arm takes it as `ik_tcp` when the robot is built. `position_cost` and `orientation_cost` weigh the two halves of the pose against each other when the solver cannot satisfy both exactly.

Every time a skill writes `x`, `y`, `z`, `rx`, `ry`, `rz`, the arm module runs this solver and sends the resulting joint angles to the servos. The reference page is [Inverse kinematics](/docs/ik).
