# The Robot

The robot is the program that owns the hardware. It talks to every actuator and sensor, reports what they measure, and carries out the actions the controller sends. This chapter writes the robot class, its first module, the six-joint arm, and the scene where simulation gives that arm a body. {{ className: 'lead' }}

## What a robot is

A robot is a Python class that extends Solarian's `Robot`. The scaffold already created yours, `MyRobotRobot` in `my_robot/robot.py`, with an arm that has no servos yet, and `my_robot/settings.py` points `ROBOT_CLASS` at it. `solarian run-robot` imports that class, builds it with the settings from `conf/robot.yaml`, and starts it.

The base class does the plumbing: it connects to the relay server, runs every device, and moves messages between the devices and the controller. Once started, the robot does the same work for the whole run:

```text
1. connect every module, to the simulator or to the hardware
2. start each module's own loop, at the rate in its YAML
3. read the modules and send the controller an observation
4. hand each action the controller sends to the modules it names
```

Your subclass says what the robot is made of, in three pieces:

- A **module** is one device: the arm, the gripper, a camera. Its class lists the device's components, its actuators and sensors, and says what to do with a command.
- The **robot** class names its modules, one class attribute each. The attribute name, `arm` here, is the module's name everywhere else in the project.
- The **scene** is the simulated world: a floor, a light, and the MuJoCo model of each module, mounted where the real device stands.

## First module: robot arm

The arm module is a Python class with one attribute per servo and a method that writes commands to them. Solarian calls that method on the module's own loop, and the same class drives the MuJoCo joints in simulation and the Feetech bus on hardware.

### Install the servo driver

The Feetech driver ships as a plugin, so install it first:

```bash
solarian install feetech
```

That installs `solarian-feetech` and adds it to your `pyproject.toml`. It brings the `FeetechServo` actuator class the arm uses, the one the scaffold left commented out. The arm module itself stays in your project.

On the machine that will later be wired to the bus, the hardware extra adds the vendor SDK:

```bash
pip install "solarian-feetech[hardware]"
```

Simulation runs without it, so leave it for the [real robot](/docs/tutorials/real-robot).

### Declare the joints

The module class declares the six servos and the arm's kinematic model. Replace `my_robot/modules/my_arm_module.py`:

```python {{ title: 'my_robot/modules/my_arm_module.py' }}
from solarian.core.arm_module import ArmModule
from solarian.core.ik import MinkIK
from solarian_feetech.actuator import FeetechServo

JOINTS = [
    "shoulder_pan",
    "shoulder_lift",
    "elbow_flex",
    "wrist_flex",
    "wrist_yaw",
    "wrist_roll",
]


class MyArmModule(ArmModule):
    shoulder_pan = FeetechServo(model="sts3250")
    shoulder_lift = FeetechServo(model="sts3250")
    elbow_flex = FeetechServo(model="sts3250")
    wrist_flex = FeetechServo(model="sts3250")
    wrist_yaw = FeetechServo(model="sts3215")
    wrist_roll = FeetechServo(model="sts3215")

    # The arm MJCF, not the scene. Joint names here are unprefixed.
    # sim_joint in the YAML stays prefixed, because that is the composed world.
    ik_backend = MinkIK(
        mjcf="assets/arm1/arm1.xml",
        joints=dict(zip(JOINTS, JOINTS)),
        frame="flange",
        position_cost=1.0,
        orientation_cost=1.0,
    )
```

The lines that matter:

- **`class MyArmModule(ArmModule)`** builds on Solarian's base class for arms. `ArmModule` already handles joint moves, so the class writes no command handling. Its `MOVE_J` takes six joint targets, plans a smooth path from where the arm is, and writes that path to the servos on the module's own loop. In simulation those servos are MuJoCo joints, and on hardware they are the bus. The class reads the same either way.
- **`shoulder_pan = FeetechServo(model="sts3250")`** declares one servo. The attribute name is the joint's name in observations, actions, and YAML. The model string picks the Feetech product: STS3250 on the four joints that carry the arm's weight, STS3215 on wrist yaw and roll.
- **`ik_backend = MinkIK(...)`** loads the arm's MuJoCo model, which you copy into the project further down this page. `MOVE_J` takes each joint in the normalized −100 to 100 range, and reads that joint's limits in radians from this model to convert it. `joints` maps each servo to the model joint of the same name. `frame="flange"` is the wrist site, and matters once the arm moves to poses in [Tutorial 4](/docs/tutorials/skills/move).

This chapter drives the arm in joint coordinates only. The same model also serves inverse kinematics, which Tutorial 4 turns on.

### Configure the module

Every module has a YAML file named after its attribute on the robot, in `conf/modules/`. It gives each servo its bus address and its range of travel. The attribute is `arm`, so the file is `conf/modules/arm.yaml`. The scaffold wrote it with only `frequency` in it.

The file reads the serial port from the deployment, so add one to `conf/deployment/localhost.yaml`. Simulation ignores it, and Tutorial 3 points it at the real adapter:

```yaml {{ title: 'conf/deployment/localhost.yaml' }}
actuator_port_arm: /dev/ttyUSB0
```

Then replace the module file, one block per joint:

```yaml {{ title: 'conf/modules/arm.yaml' }}
actuator_port: ${deployment.actuator_port_arm}
frequency: 50

actuators:
  shoulder_pan:
    id: 1
    port: ${actuator_port}
    mode: range_m100_100
    sim_joint: "arm/shoulder_pan"
    sim_range_min: -2.2290
    sim_range_max: 2.0820
  shoulder_lift:
    id: 2
    port: ${actuator_port}
    mode: range_m100_100
    sim_joint: "arm/shoulder_lift"
    sim_range_min: -1.7988
    sim_range_max: 1.7802
  elbow_flex:
    id: 3
    port: ${actuator_port}
    mode: range_m100_100
    sim_joint: "arm/elbow_flex"
    sim_range_min: -1.7802
    sim_range_max: 1.5708
  wrist_flex:
    id: 4
    port: ${actuator_port}
    mode: range_m100_100
    sim_joint: "arm/wrist_flex"
    sim_range_min: -3.1416
    sim_range_max: 3.1416
  wrist_yaw:
    id: 5
    port: ${actuator_port}
    mode: range_m100_100
    sim_joint: "arm/wrist_yaw"
    sim_range_min: -3.1416
    sim_range_max: 3.1416
  wrist_roll:
    id: 6
    port: ${actuator_port}
    mode: range_m100_100
    sim_joint: "arm/wrist_roll"
    sim_range_min: -3.1416
    sim_range_max: 3.1416
```

The lines that matter:

- **`frequency: 50`** is the rate of the module's loop, in hertz: how often the module writes its path to the servos. The controller runs at its own, slower rate, and the two are independent.
- **`id`** is the servo's address on the Feetech bus. You set those IDs on the real servos in Tutorial 3.
- **`mode: range_m100_100`** makes every command a normalized number: −100 is one end of the joint's travel, 100 is the other, and 0 is the middle.
- **`sim_joint`** names the MuJoCo joint this servo drives. The `arm/` in front is the prefix the scene gives the arm, further down this page.
- **`sim_range_min`** and **`sim_range_max`** are that same travel in radians, copied from the model's joint limits. Simulation maps −100…100 onto them. Hardware uses a calibration instead, recorded in Tutorial 3, and ignores the `sim_*` lines.

## Add the arm to the robot

The robot class is where the module joins the machine. One class attribute creates the module, and its name, `arm`, ties together the YAML file above, the observation and action fields of the next chapter, and every log line about the arm. The scaffold already wrote that line in `my_robot/robot.py`:

```python {{ title: 'my_robot/robot.py' }}
from solarian.core import Robot

from my_robot.modules.my_arm_module import MyArmModule


class MyRobotRobot(Robot):
    arm = MyArmModule()
```

When the robot starts, Solarian finds `arm`, loads `conf/modules/arm.yaml` into it, connects it, and runs its loop. A second arm later is one more line with another name, such as `left_arm = MyArmModule()`, configured by its own `conf/modules/left_arm.yaml`.

## Place the arm in the scene

In simulation the module needs a body: the arm's MuJoCo model, standing in a world with a floor. This section copies the model into the project, writes a small world around it, and tells the robot where the arm stands in that world.

### Copy the arm model

The model is published with the [`solarian-arm1`](https://github.com/solarian-dev/solarian-arm1) package. Copy its assets folder into the project. This copies data only: the module class is the file you just wrote. `solarian-arm1` also ships a maintained version of the same module, for projects that would rather install it than keep it.

```bash
git clone --depth 1 https://github.com/solarian-dev/solarian-arm1.git /tmp/solarian-arm1
mkdir -p assets
cp -R /tmp/solarian-arm1/solarian_arm1/assets assets/arm1
```

You should now have `assets/arm1/arm1.xml` and an `arm1_description/` folder of meshes beside it. The XML finds its meshes by a path relative to itself, so keep the two together.

The arm model has a site named `flange` at the wrist. The gripper bolts to it in a later chapter.

### Write the world

The world around the arm holds what every scene shares: a floor and a light. Create `assets/scene.xml`:

```xml {{ title: 'assets/scene.xml' }}
<mujoco model="my_robot_scene">
  <compiler angle="radian"/>
  <visual>
    <headlight diffuse="0.6 0.6 0.6" ambient="0.3 0.3 0.3"/>
    <global azimuth="120" elevation="-20"/>
  </visual>
  <asset>
    <texture type="skybox" builtin="flat" rgb1="0.6 0.6 0.6" width="512" height="512"/>
    <texture name="grid" type="2d" builtin="checker" rgb1="0.2 0.3 0.4" rgb2="0.1 0.15 0.2"
             width="512" height="512" mark="edge" markrgb="0.8 0.8 0.8"/>
    <material name="grid" texture="grid" texrepeat="8 8"/>
  </asset>
  <worldbody>
    <light pos="0 0 1.5" dir="0 0 -1" directional="true"/>
    <geom name="floor" type="plane" size="1 1 0.05" material="grid"/>
  </worldbody>
</mujoco>
```

The arm stays out of this file. The robot attaches it in Python, which keeps the arm model reusable in any other scene. The skybox is a flat grey. The camera chapter is why: a fisheye leaves black corners, and a black sky would hide the edge of the lens.

### Attach the arm

The robot class carries the scene, and the scene lists one attachment per module that has a body. Each attachment says which model belongs to which module and where it is mounted, the same way you would bolt the real arm to a table. Extend `MyRobotRobot`:

```python {{ title: 'my_robot/robot.py' }}
from solarian.core import Robot
from solarian.sim import ModuleAttachment, SceneConfig

from my_robot.modules.my_arm_module import MyArmModule


class MyRobotRobot(Robot):
    arm = MyArmModule()

    scene = SceneConfig(
        world_mjcf="assets/scene.xml",
        attachments=[
            ModuleAttachment(
                module="arm",
                mjcf="assets/arm1/arm1.xml",
                parent_body="world",
                pos=[0.0, -0.2, 0.0],
                prefix="arm/",
            ),
        ],
        timestep=0.002,
    )
```

The lines that matter:

- **`scene`** is what lets the robot run in MuJoCo. You choose sim per run with `solarian run-robot --sim`; without the flag the same class drives the hardware. In sim the servos become the model's joints, and the module class does not change. Add `--view` to watch the simulation in a window.
- **`world_mjcf`** is the world you just wrote.
- **`module="arm"`** pairs the attachment with the module of that name, so the module's servos drive this model's joints.
- **`parent_body="world"`** and **`pos=[0.0, -0.2, 0.0]`** bolt the arm's base to the world, 20 cm along −Y from the origin, on the floor.
- **`prefix="arm/"`** renames the model's joints inside the scene, so `shoulder_pan` becomes `arm/shoulder_pan`. That is why the YAML's `sim_joint` lines carry the prefix. It also lets a second arm join later without its joint names colliding.
- **`timestep=0.002`** steps the physics at 500 Hz.

<Note>
  You can start the robot now with <code>solarian run-robot --sim --view</code>. The sim window should show the arm at mid-travel, holding still, because nothing sends it a command yet. A missing <code>arm1.xml</code> fails at startup with a file error. A <code>sim_joint</code> that does not match the prefixed model name fails when the world is built, and the message names the joint.
</Note>
