# The Controller

The controller is the program that decides what the robot does. It runs a loop, and on every tick it turns what has happened since the last tick into actions for the robot. This chapter writes a teleop skill, where each key nudges one joint of the arm, and a controller that starts it. {{ className: 'lead' }}

The keyboard is the input device here because every computer has one. A controller can read any other hardware the same way: a joystick or gamepad, a space mouse that moves the hand in six directions at once, or a leader arm, a second arm you move by hand while the robot copies its joints. Each of those becomes a module on the controller, the way the keyboard already is one, and a skill reads it.

## What a controller is

A controller is a Python class that extends Solarian's `Controller`. The scaffold already created yours, an empty `MyRobotController` in `my_robot/controller.py`, and `my_robot/settings.py` points `CONTROLLER_CLASS` at it. `solarian run-controller` imports that class, builds it with the settings from `conf/controller.yaml`, and starts its loop.

The base class does the plumbing: it connects to the relay server, receives every observation the robot sends, and runs the loop. What the robot does is written as **skills**, and the controller decides which skill runs:

- A **skill** is one behavior: jog the joints from the keyboard, open the gripper, go to a pose. It reads observations and events, and returns actions.
- The **controller** lists the skills it can start and binds keys to them.

Each tick of the loop runs the same steps, in the same order:

```text
1. collect events from the controller's modules, and run every matching event handler
2. update the controller's own modules, such as the keyboard
3. hand the same events to every running skill
4. step the skills, and send the actions they returned to the robot
5. wait for the next tick, fps times per second
```

`fps` comes from `conf/controller.yaml`, and the scaffold sets it to 30. Handlers run first, so a key that starts a skill takes effect on the same tick.

## The controller window

Keys reach the controller through its front end, the UI. The default is a pygame window: it receives real key presses and releases, and from [the camera chapter](/docs/tutorials/first-robot/camera) on it shows the wrist camera's picture. On a machine without a display, `ui: console` in `conf/controller.yaml` runs the controller from the terminal instead, which shows telemetry and reads characters as you type.

## Events

An **event** is a record of something that happened at one instant: a key went down, a key came up, an image was clicked. Modules produce events. Every controller carries a keyboard module, and it emits a `KEY_DOWN` event when a key is pressed and a `KEY_UP` when it is released. `event.data["key"]` is the key, as a lowercase character.

Solarian collects the events at the start of each tick, in the order they happened. The controller reacts to them in **event handlers**, and every running skill gets the same list in `self.events`.

## The teleop skill

The teleop skill keeps a joint target for the arm. Each key press moves one joint of that target, and the skill sends the whole target to the arm. The scaffold already made `my_robot/skills/` a package, the way the arm module lives in `modules/`. Create `my_robot/skills/teleop.py`:

```python {{ title: 'my_robot/skills/teleop.py' }}
from solarian.core.action import Action, ActionType
from solarian.core.event import EventType
from solarian.core.execution import ExecutionMode
from solarian.core.skill import Skill

# One key pair per joint: the first decreases, the second increases.
_KEYS = {
    "q": ("shoulder_pan", -5),
    "a": ("shoulder_pan", 5),
    "w": ("shoulder_lift", -5),
    "s": ("shoulder_lift", 5),
    "e": ("elbow_flex", -5),
    "d": ("elbow_flex", 5),
    "u": ("wrist_flex", -5),
    "j": ("wrist_flex", 5),
    "i": ("wrist_yaw", -5),
    "k": ("wrist_yaw", 5),
    "o": ("wrist_roll", -5),
    "l": ("wrist_roll", 5),
}
JOINTS = sorted({joint for joint, _ in _KEYS.values()})


class JointTeleopSkill(Skill):
    # Runs on the controller's own tick, so a key press moves the arm
    # on the tick it arrives.
    execution_mode = ExecutionMode.INLINE

    def setup(self):
        self._target = None

    def control_step(self, dt):
        arm = self.params["arm"]
        if self._target is None:
            obs = self.observations[arm].latest()
            if obs is None:
                return None
            self._target = {joint: float(obs[joint].value) for joint in JOINTS}
        steps = [
            _KEYS[event.data["key"]]
            for event in self.events
            if event.type == EventType.KEY_DOWN and event.data["key"] in _KEYS
        ]
        if not steps:
            return None
        for joint, delta in steps:
            self._target[joint] = max(-100.0, min(100.0, self._target[joint] + delta))
        return Action(
            action_type=ActionType.MODULE_ACTION,
            data={
                arm: {
                    "action_type": ActionType.MOVE_J,
                    "data": {j: {"value": v} for j, v in self._target.items()},
                },
            },
        )
```

The lines that matter:

- **`execution_mode = ExecutionMode.INLINE`** runs the skill on the controller's loop. A skill can also run in its own process, which a policy needs. A key handler does not.
- **`setup`** runs each time the skill starts. It forgets the old target.
- **`self.observations[arm].latest()`** is the newest observation of the arm. On its first step the skill copies the measured joints into its target, so a restarted teleop jogs from wherever the arm is and does not snap back to an old target.
- **`self.events`** holds this tick's events. The skill keeps the `KEY_DOWN`s it has a joint for.
- **`self._target[joint]`** moves 5 units per press and is clamped to −100…100, the joint's full travel.
- **`ActionType.MOVE_J`** is `ArmModule`'s joint move. The action carries all six joints, and the module plans its path from where the arm is.
- **`self.params["arm"]`** is the arm module's name. The skill never imports the robot. The name is the whole address, which is what lets the same skill drive another arm.

On a tick with no key the skill returns `None`, and the arm keeps going toward the last target. Holding a key still gives one step: the keyboard module reports the press once, so press again to move further.

## Start it from the controller

The controller names the skills it can start, and starts teleop as soon as it runs. Replace `my_robot/controller.py`:

```python {{ title: 'my_robot/controller.py' }}
from solarian.core import Controller
from solarian.core.event import Event, EventType, event_handler
from solarian.core.skill import Tool

from my_robot.skills.teleop import JointTeleopSkill


class MyRobotController(Controller):
    tools = {
        "teleop": Tool(JointTeleopSkill, {"arm": "arm"}),
    }

    def on_start(self):
        self.start_tool("teleop")

    @event_handler(EventType.KEY_DOWN)
    def start_bound_skill(self, event: Event):
        if event.data["key"] == "0":
            self.start_tool("teleop")
```

The lines that matter:

- **`tools`** names the ways this controller starts a skill: a skill class plus the params bound to it. `{"arm": "arm"}` tells teleop which module to drive.
- **`start_tool("teleop")`** builds the skill and starts it. Starting a skill stops any other skill commanding the same module, so a key press replaces the current behavior and never stacks on it.
- **`on_start`** runs once the controller's loop is up. Teleop is running before you touch a key.
- **`@event_handler(EventType.KEY_DOWN)`** registers `start_bound_skill` for key presses. The method name is yours. `0` starts teleop again, after another skill has taken the arm or after space stopped it.

The controller does not define `control_step`. The base class's version steps the running skills and sends what they return, so the controller stays a list of skills and the keys that start them.

Several handlers can share an event type, and all of them run, the base class's first. `Controller` brings three key handlers of its own, and they keep working next to yours: space stops every running skill, `r` starts and stops a recording, and delete throws the current recording away.

## The keys

The letters run in pairs down the keyboard, one pair per joint from the shoulder to the wrist:

| Joint | Decrease | Increase |
| --- | --- | --- |
| shoulder pan | `q` | `a` |
| shoulder lift | `w` | `s` |
| elbow | `e` | `d` |
| wrist flex | `u` | `j` |
| wrist yaw | `i` | `k` |
| wrist roll | `o` | `l` |

`0` restarts teleop. `r` is the base class's recording key, and it is not in the table. In Tutorial 4 more number keys start more skills, and the letters stay with teleop.
