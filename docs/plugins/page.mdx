# Plug-ins

Solarian's core framework doesn't ship hardware drivers. Every actuator, sensor, and module that talks to a real robot lives in a standalone **plugin package** named `solarian-<name>`. This keeps the framework slim and lets the community ship drivers independently. {{ className: 'lead' }}

## What is a plugin?

A Solarian plugin is a normal Python package that:

1. Has the prefix **`solarian-`** in its distribution name (e.g. `solarian-ur5`).
2. Imports under a snake_case module name (e.g. `solarian_ur5`).
3. Provides one or more of: `Module` subclasses, `Actuator` / `Sensor` subclasses, and `ComponentBus` subclasses.
4. Ships a default Hydra config (`conf.yaml`) inside the package, used by `solarian add-module` to seed your project.

A plugin is just a Python package — there is no special "register me" call your project has to make. You import the classes you want and attach them to your `Robot` or `Module`.

## Using a plugin

The fastest path is `solarian add-module`. It installs the plugin from PyPI **and** copies its bundled default config into your project's `conf/` directory:

```bash
solarian add-module ur5 arm
# 1. pip install solarian-ur5
# 2. copy solarian-ur5/.../conf.yaml → conf/arm.yaml
```

The first argument (`ur5`) is the plugin name; the second (`arm`) is the **attribute name** you'll use on your `Robot`. The two pieces are independent: you can install `ur5` once and attach it as `left_arm` and `right_arm` on a bimanual robot.

Then attach the module to your `Robot`:

```python
from solarian.core import Robot
from solarian_ur5.module import UR5ArmModule

class MyRobot(Robot):
    arm = UR5ArmModule()
```

Edit `conf/arm.yaml` to set ports, IDs, frequency, and calibration paths for your specific hardware.

## Anatomy of a module plugin

A plugin like `solarian-ur5` is structured like any other Python package:

```text
solarian-ur5/
├── pyproject.toml
└── solarian_ur5/
    ├── __init__.py
    ├── actuator.py     # UR5JointActuator, UR5CartesianActuator
    ├── bus.py          # UR5Bus(ActuatorBus)
    ├── module.py       # UR5ArmModule(Module), UR5ArmConfig
    └── conf.yaml       # default config copied by `add-module`
```

### Actuator subclass

Each actuator binds a `bus_class` and declares its `Data` channels:

```python
from solarian.core.servo import Servo
from solarian.core.data import PosData, SpeedData
from solarian_ur5.bus import UR5Bus

class UR5JointActuator(Servo):
    bus_class = UR5Bus
    pos = PosData()
    speed = SpeedData()
```

### Bus subclass

The bus implements the protocol-speaking part. Subclasses of `ActuatorBus` add `write()`, `enable_torque()`, `disable_torque()`; subclasses of `SensorBus` add sensor-specific reads. See [Core](/docs/core) for the full contract.

### Module subclass

The module attaches actuators and sensors as class attributes, optionally with a per-module `config_class`:

```python
from solarian.core.module import Module
from solarian.core.configs import ModuleConfig
from solarian_ur5.actuator import UR5JointActuator, UR5CartesianActuator

class UR5ArmConfig(ModuleConfig):
    calibration_file: str | None = None

class UR5ArmModule(Module):
    config_class = UR5ArmConfig

    shoulder_pan = UR5JointActuator()
    shoulder_lift = UR5JointActuator()
    elbow_flex = UR5JointActuator()
    wrist_flex = UR5JointActuator()
    wrist_yaw = UR5JointActuator()
    wrist_roll = UR5JointActuator()

    x = UR5CartesianActuator()
    y = UR5CartesianActuator()
    z = UR5CartesianActuator()
    rx = UR5CartesianActuator()
    ry = UR5CartesianActuator()
    rz = UR5CartesianActuator()
```

### Default `conf.yaml`

Bundle a sensible starting config inside the plugin package. `solarian add-module` reads it and writes it out to `conf/<attr>.yaml` in the user's project. See [`projects/ur5/conf/arm.yaml`](https://github.com/solarian-dev/solarian/blob/main/projects/ur5/conf/arm.yaml) for the UR5 example.

## Anatomy of an actuator plugin

When you only want to ship an actuator + bus (no opinionated module), you can skip the `Module` class:

```text
solarian-dynamixel/
├── pyproject.toml
└── solarian_dynamixel/
    ├── actuator.py     # DynamixelServo
    └── bus.py          # DynamixelBus
```

```python
from solarian.core.servo import Servo
from solarian.core.data import PosData, SpeedData
from solarian_dynamixel.bus import DynamixelBus

class DynamixelServo(Servo):
    bus_class = DynamixelBus
    pos = PosData()
    speed = SpeedData()
```

End-users compose their own modules with your servos:

```python
from solarian.core.module import Module
from solarian_dynamixel.actuator import DynamixelServo

class MyArmModule(Module):
    shoulder = DynamixelServo()
    elbow = DynamixelServo()
    gripper = DynamixelServo()
```

## Anatomy of a sensor plugin

Same shape as an actuator plugin, but using `Sensor` and `SensorBus`:

```python
from solarian.core.sensor import Sensor
from solarian.core.data import ImageData
from solarian_camera.bus import CameraBus

class RGBCamera(Sensor):
    bus_class = CameraBus
    rgb_image = ImageData(shape=(480, 640, 3))
```

The bus implements `read(ImageData, [...])` by grabbing a frame from V4L2 / AVFoundation / RealSense / whatever your sensor needs.

## Entry-point registration (optional)

Solarian's `pyproject.toml` defines two entry-point groups for plugin discovery:

```toml
[project.entry-points."solarian.modules"]
my_arm = "my_package.modules:MyArmModule"

[project.entry-points."solarian.actuator_buses"]
my_bus = "my_package.buses:MyBus"
```

Plugins that publish entry points become enumerable through `solarian.plugins` helpers. **Direct imports work fine without entry points** — most plugins (including the in-repo `solarian-ur5`) currently rely on direct imports plus `solarian add-module`'s convention-based config copying.

## Mixing actuator types in a module

Modules can mix and match actuator types from different plugins:

```python
from solarian.core.module import Module
from solarian_feetech.actuator import FeetechServo
from solarian_dynamixel.actuator import DynamixelServo
from solarian_ur5.actuator import UR5JointActuator

class MixedModule(Module):
    shoulder = FeetechServo(id=1, model="sts3215")
    elbow = FeetechServo(id=2, model="sts3215")
    gripper = DynamixelServo(id=1, model="xl330-m077")
    base_joint = UR5JointActuator(id=0, model="ur5")
```

Each actuator's `bus_class` ensures the right bus is used for its hardware. If two actuators share a port, they go on the same bus instance; if not, the module gets one bus per port.

## Publishing your own plugin

To publish a plugin to PyPI:

1. Create a new package named `solarian-<name>` with `solarian` listed as a dependency.
2. Pick a snake_case import name (`solarian_<name>`) and put your `Module` / `Actuator` / `Sensor` / `Bus` classes in there.
3. Ship a default `conf.yaml` inside the package so `solarian add-module` can seed user projects.
4. (Optional) Declare entry points under `solarian.modules` and `solarian.actuator_buses` in your `pyproject.toml`.
5. Publish with `python -m build && twine upload dist/*` (or your favorite alternative).

That's it — users install your plugin with `pip install solarian-<name>` (or `solarian add-module <name> <attr>`) and reference your classes in their own code.
