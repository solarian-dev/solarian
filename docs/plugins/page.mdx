# Plugins

Solarian's core framework ships almost no batteries: no hardware drivers, no policies, no robot definitions. Everything that talks to real hardware or adds a capability lives in a standalone **plugin package** named `solarian-<name>`. This keeps the core slim and lets anyone publish and share extensions independently. {{ className: 'lead' }}

This page explains what a plugin is and the kinds you can build. Browse published packages in the [Plugin Directory](/plugins), see [Using Plugins](/docs/using-plugins) to install and wire one into a project, and [Creating Plugins](/docs/creating-plugins) to scaffold and publish your own.

## What is a plugin?

A Solarian plugin is a normal, `pip`-installable Python package that follows two conventions:

1. Its distribution name is prefixed **`solarian-`** (e.g. `solarian-feetech`).
2. It imports under the matching snake_case module name (e.g. `solarian_feetech`).

Beyond that, it just provides one or more Solarian classes — an `Actuator`, a `Bus`, a `Module`, a `Robot`, a `Skill`, a policy `Trainer`/`PolicyServer`, or a CLI command — and (optionally) advertises them through **entry points** so Solarian can discover them automatically.

<Note>
  There is no mandatory "register me" call. Direct imports always work: `from solarian_feetech.actuator import FeetechServo`. Entry points are what make a plugin *discoverable* — so `solarian add-module`, the `AIController`, and `solarian train` can find your classes by name without the user importing anything.
</Note>

## Kinds of plugins

A single package can ship any combination of these. The type determines which files you write and which entry-point groups the classes register under.

<Properties>
  <Property name="Hardware — actuator / sensor">
    A driver for a motor, servo, or sensor plus the <a href="/docs/core">Bus</a> that speaks its protocol. Registers under <code>solarian.actuators</code> / <code>solarian.actuator_buses</code> (or <code>solarian.sensors</code> / <code>solarian.sensor_buses</code>). Example: <code>solarian-feetech</code>, <code>solarian-dynamixel</code>.
  </Property>
  <Property name="Module">
    An opinionated <a href="/docs/modules">Module</a> that composes actuators/sensors into a ready-to-use unit (an arm, a gripper), usually with a bundled <code>conf.yaml</code>. Registers under <code>solarian.modules</code>. Example: <code>solarian-ur5</code>, <code>solarian-umi-slim</code>.
  </Property>
  <Property name="Robot">
    A full <a href="/docs/robots">Robot</a> definition wiring several modules together. Registers under <code>solarian.robots</code>.
  </Property>
  <Property name="Skill">
    A self-contained <a href="/docs/skills">Skill</a> behavior the <a href="/docs/ai_controller">AI Controller</a> can orchestrate. Registers under <code>solarian.skills</code> and is auto-discovered by any <code>AIController</code>. Example: <code>solarian-skill-cup-arrange</code>.
  </Property>
  <Property name="Policy">
    A trainable model: a <code>Trainer</code> (for <code>solarian train</code>) and/or a <code>PolicyServer</code> a skill calls over HTTP. Registers under <code>solarian.trainers</code> (and often <code>solarian.skills</code>). Example: <code>solarian-policy-diffusion</code>. See <a href="/docs/policies">Policies</a>.
  </Property>
  <Property name="Command">
    A custom <code>solarian</code> subcommand. Registers under <code>solarian.commands</code>. Example: <code>solarian feetech-set-id</code> shipped by <code>solarian-feetech</code>.
  </Property>
</Properties>

## Entry-point groups

Discovery is powered by standard Python entry points read via `importlib.metadata`. Each plugin type maps to one or more groups:

| Plugin type | Entry-point group(s) | Discovered by |
| --- | --- | --- |
| Actuator | `solarian.actuators`, `solarian.actuator_buses` | config `type:` resolution |
| Sensor | `solarian.sensors`, `solarian.sensor_buses` | config `type:` resolution |
| Module | `solarian.modules` | `solarian add-module` |
| Robot | `solarian.robots` | project wiring |
| Skill | `solarian.skills` | `AIController` |
| Policy | `solarian.trainers` (+ `solarian.skills`) | `solarian train`, `run-policy` |
| Command | `solarian.commands` | `solarian` CLI |

## Available plugins

Browse every published listing — official and community — in the [Plugin Directory](/plugins). You can also [submit a plugin](/plugins/submit) for review.

The Solarian organization ships these reference plugins (under [`plugins/`](https://github.com/solarian-dev/solarian/tree/main/plugins) in the monorepo):

<Properties>
  <Property name="solarian-ur5">
    Universal Robots UR5 arm — joint- and Cartesian-space actuators plus a complete <code>UR5ArmModule</code>.
  </Property>
  <Property name="solarian-dynamixel">
    Dynamixel servos (XL330, XM430, …) and the <code>DynamixelBus</code>.
  </Property>
  <Property name="solarian-feetech">
    Feetech servos (STS3215, SCS, …), the <code>FeetechBus</code>, and a <code>feetech-set-id</code> command.
  </Property>
  <Property name="solarian-koch / solarian-so100">
    Arm modules built on Feetech servos.
  </Property>
  <Property name="solarian-lekiwi">
    Lekiwi mobile-base module.
  </Property>
  <Property name="solarian-umi-gripper / solarian-umi-slim">
    UMI gripper modules (the slim variant ships its own MuJoCo model for simulation).
  </Property>
  <Property name="solarian-skill-cup-arrange">
    A UMI diffusion-policy skill, auto-discovered via <code>solarian.skills</code>.
  </Property>
  <Property name="solarian-policy-diffusion / solarian-policy-lerobot">
    Policy plugins that train and serve models the skills call.
  </Property>
</Properties>
