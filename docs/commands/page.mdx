# Command Line Interface

Solarian ships two console scripts:

- **`solarian`** — the main CLI. Every project workflow (running a node, recording, training, …) goes through this command.
- **`create-solarian`** — a one-shot project scaffolder. See [Creating a Project](/docs/creating-a-project).

Run `solarian --help` to print the grouped command list.

## Global flags

Every `solarian` subcommand accepts these top-level flags before the subcommand name:

<Properties>
  <Property name="--conf" type="string">
    Path to the Hydra config directory. Defaults to <code>conf</code>. You can also pass <code>dir/name</code> to override the config name (for example, <code>--conf conf/robot_dev</code>).
  </Property>
  <Property name="--deployment, -d" type="string">
    Deployment profile in <code>conf/deployment/</code>, supplying the relay address and device ports for this host layout. Defaults to <code>$SOLARIAN_DEPLOYMENT</code>, then <code>localhost</code>. See <a href="/docs/project-configs#deployments">Deployments</a>.
  </Property>
  <Property name="--settings" type="string">
    Path to your project's <code>settings.py</code>. Auto-discovered when omitted (looks for <code>{`{package_name}`}/settings.py</code> based on <code>pyproject.toml</code>, then <code>conf/settings.py</code>).
  </Property>
  <Property name="--version, -V" type="flag">
    Print the installed Solarian version and exit. Works on its own, without a subcommand.
  </Property>
</Properties>

Hydra-style overrides on the command line (`key=value`) are forwarded to the underlying Hydra `compose()` call, so anything in your YAML can be overridden ad hoc.

```bash
solarian run-robot fps=60 connection.ip=192.168.1.20
```

Some commands also take parameters that are not YAML keys at all — `role`, `module`, `sweep`, `axis`. Hydra composes in struct mode and would normally reject those, so a command declares them in a `params` tuple and they are seeded before your overrides are applied:

```python
class CalibrateCameraLatencyCommand(BaseCommand):
    params = ("role", "monitor_hz", "qr_size", "n_frames", "plot", "allow_unsynced")
```

You then write them plainly, `role=display`, with no `+` prefix. A name that is neither a YAML key nor a declared parameter is still rejected, which is what catches `frps=60` before it silently does nothing.

## Project commands

### `create-project`

```bash
solarian create-project <project_name> [--force]
```

Scaffolds a new project. Prefer the standalone `create-solarian <name>` script — it's the same code, but works before a Solarian project exists in the current directory.

### `add-module`

```bash
solarian add-module <plugin_name> <attr_name>
```

Installs a hardware plugin (`solarian-<plugin_name>`) and copies the plugin's bundled `conf.yaml` to `conf/<attr_name>.yaml`. The `attr_name` must match the attribute you'll use on your `Robot` subclass — see [Project Configs](/docs/project-configs).

```bash
solarian add-module ur5 arm
solarian add-module feetech gripper
```

## Robot commands

These commands run on the robot machine. They import the modules listed under <code>setup_modules=("robot", "observation", "action")</code>.

### `run-robot`

```bash
solarian run-robot
```

Loads `conf/robot.yaml`, instantiates your `Robot` subclass, spawns one process per `Module`, and starts the action receiver / observation publisher. See [Robots](/docs/robots).

### `calibrate`

```bash
solarian calibrate
```

Interactive bring-up for one module. Four steps on an IK arm: **Step 1: Joint limits**, **Step 2: Home position** (match the static model-q=0 sim), **Step 3: Sim mapping** (highlighted joint, Y/N), **Output**. The live mirror then stays open with on-screen nrm / rad numbers so you can check the mapping. Answer ENTER / Y / N in the sim window. Grippers stop after Step 1 plus one physical closed pose. See [Calibration](/docs/modules/calibration).

### `calibrate-arm-latency`

```bash
solarian calibrate-arm-latency [axis=z] [amplitude=0.02] [freq=1.25]
```

Measures one of the two latencies a UMI skill needs for an `ArmModule`. You pick the arm (auto-selected when there is only one) and a mode:

- **action** — sweep a Cartesian sinusoid on one axis, record the measured pose, and recover the command-to-motion delay by cross-correlation. Prints `arm_action_latency` and shows alignment plots. Refuses to run if the sinusoid's peak velocity would exceed the module's `max_speed`, which would measure the speed limit instead of the pipeline.
- **obs** — time a few hundred pose reads and report the mean, which is `arm_obs_latency`.

Action mode records where the arm started, then walks you through placing it by hand: take hold, Enter to release torque, position it, Enter to lock it there, let go, Enter to record. It then verifies the model can travel the full amplitude both ways from that pose and aborts naming the joint in the way, because an out-of-reach sweep comes back clipped and the clip is what gets measured. Afterwards the arm returns to the safe pose you chose and then to where it was when the command started, including when the run aborts partway. See [Latency & Synchronization](/docs/latency) for what each number corrects and why.

### `calibrate-arm-speed`

```bash
solarian calibrate-arm-speed [poses=3] [distance=0.06]
```

Measures the Cartesian translation speed the arm actually sustains, which is `max_speed[0]` in the arm's module yaml. Run this **before** `calibrate-arm-latency`, which sizes its sweep against that limit.

You free-drive the arm to each pose in turn, through the same take-hold / release-torque / lock / let-go prompts as `calibrate-arm-latency`. At the first direction it ramps the commanded speed until the measured motion stops keeping up, then checks whether every other pose and axis direction can hold that same speed, lowering it whenever one cannot. Between directions the arm drives back to the pose you chose rather than reversing the offset it just made, so a move that fell short does not shift where the next one begins. What it reports is the slowest sample, since the Jacobian means a single global limit is only safe if it is the minimum over the region the arm works in. Directions without room for the full test distance are skipped rather than measured short. The arm returns to its original pose when the command ends.

The moves deliberately run above the configured limit — that is the only way to see past it — with a ceiling of four times the configured value.

### `calibrate-gripper-speed`

```bash
solarian calibrate-gripper-speed
```

The same idea for the jaws, filling `max_speed` in the gripper's module yaml. This one is a genuine hardware constant: one prismatic degree of freedom, no Jacobian, so a single measurement holds everywhere. It strokes between the ends of travel (staying a tenth clear of the hard stops) at rising speed and reports the rate the jaws hold, along with whether the configured value is optimistic, pessimistic, or fair.

### `calibrate-gripper-latency`

```bash
solarian calibrate-gripper-latency
```

The same two modes for any `GripperModule` (UMI `calibrate_gripper_latency`): a sinusoid across the configured aperture range for `gripper_action_latency`, or read timing for `gripper_obs_latency`. The two are **not** the same number and correct in opposite directions — see [Latency & Synchronization](/docs/latency).

### `calibrate-gripper-ranges`

```bash
solarian calibrate-gripper-ranges
```

Sweeps the servo across its normalized range and asks you for a ruler reading (mm) at each stop, then writes the pairs to `aperture_table` in the module yaml (UMI `calibrate_gripper_ranges`). That table is what `GripperModule` interpolates to turn a commanded aperture into a servo value. Without it the module assumes the opening is a straight line between `aperture_closed_mm` and `aperture_open_mm`, which a parallel gripper's linkage does not follow.

### `calibrate-camera-latency`

```bash
# on the machine with a monitor
solarian calibrate-camera-latency role=display [monitor_hz=60] [qr_size=720]

# on the robot, camera pointed at that monitor
solarian calibrate-camera-latency role=capture monitor_hz=60 [n_frames=120] [plot=true]
```

Measures `camera_obs_latency` with UMI's QR-timestamp method: one role fills a screen with a QR code encoding the instant it was drawn, the other films it and subtracts. `monitor_hz` is required on `capture`, where display refresh enters the arithmetic, and optional on `display`, where it only paces the redraw. Both roles sync to the relay clock, so the screen and the camera can be on different machines — which is the better setup, though both can share one machine if the robot has a screen. See [Latency & Synchronization](/docs/latency).

All four `calibrate-*` commands above talk to the module in-process (same as `solarian calibrate`), not through the robot's action queues. Run them on the machine the device is wired to, with `run-robot` stopped — the only exception is `calibrate-camera-latency role=display`, which just draws on a screen and belongs on the machine with the monitor. See [Latency & Synchronization](/docs/latency).

### `setup-module`

```bash
solarian setup-module module_name=<attr>
```

Interactive helper for setting up a hardware module — assigning servo IDs, picking a port, and writing the resulting values into `conf/<attr>.yaml`.

### `calibrate-servo`

```bash
solarian calibrate-servo
```

Prepares one servo for use, before it is a module component: pick the brand, the port and the servo, then set its ID, reset the comms and position registers, and park the shaft at mid-encoder so you can fit the horn with the mechanism at mid-travel. Needs no project and no config.

Do this on every new servo. A horn fitted at an arbitrary shaft angle can put the `0/4095` encoder seam inside the joint's travel, which [Calibration](/docs/modules/calibration) has to reject — the servo cannot be commanded across the seam. The brand menu lists every installed actuator bus plugin; a brand whose plugin has no scanning support says so instead of failing.

### `write-robot-calibration`

```bash
solarian write-robot-calibration
```

Writes the calibration values listed in your YAML into the actuators / sensors themselves (e.g. servo offsets stored on the device EEPROM). Re-pushes an existing [calibration](/docs/modules/calibration) file without re-sweeping.

### `verify-calibration`

```bash
solarian verify-calibration module=<attr>
```

Compares each joint's calibrated span (in radians) to the IK model's `jnt_range` and prints a per-joint PASS/FAIL table. On an arm it then opens the live sim mirror so you can move the real arm and confirm the sim tracks. See [Calibration](/docs/modules/calibration).

### `derive-model-limits`

```bash
solarian derive-model-limits module=<attr> [sweep=true]
```

Prints MJCF-ready joint `range="lo hi"` values (radians) derived from the real arm's mechanical limits — from the existing calibration, or a guided live sweep with `sweep=true`. For model authors keeping `jnt_range` equal to the real hard-stops. See [Calibration](/docs/modules/calibration).

## Controller commands

These run on the controller machine. They import <code>setup_modules=("controller", "observation", "action")</code>.

### `run-controller`

```bash
solarian run-controller
```

Loads `conf/controller.yaml`, instantiates your `Controller` (or `AIController`) subclass, and starts the action sender / observation receiver. See [Controllers](/docs/controllers).

### `calibrate-controller`

```bash
solarian calibrate-controller
```

Runs controller-side calibration. Used for leader-arm setups where the *controller* hardware also needs zeroing.

### `write-controller-calibration`

```bash
solarian write-controller-calibration
```

Writes the calibration values from YAML into the controller hardware.

### `run-policy`

```bash
solarian run-policy <skill_name> [--checkpoint PATH] [--host HOST] [--port PORT]
```

Runs the [`PolicyServer`](/docs/servers) associated with a skill. The skill declares its server via the `policy_server_module` class attribute and the checkpoint location in its bundled config (`policy_server.checkpoint`); this command resolves both and launches the server (overridable with `--checkpoint`/`--host`/`--port`). For example, `solarian run-policy cup_arrange` starts the diffusion policy server that `solarian-skill-cup-arrange` drives. See [Training](/docs/training) and [Skills](/docs/skills).

### `run-server`

```bash
solarian run-server
```

Starts a [`RelayServer`](/docs/servers) using `conf/server.yaml`. Run this on the relay machine — typically a small box on the same network as both the robot and the controller.

## Recording & replay commands

### `record`

```bash
solarian record num_episodes=10 episode_time_s=20
```

Records teleoperated episodes by simultaneously running the controller and observation receiver, then writes the result to disk in the format declared by `conf/record.yaml` (`repo_id`, `tasks`, video options). Imports robot, observation, action, and controller modules.

### `replay`

```bash
solarian replay episodes=[0,1,2]
```

Replays a previously recorded episode by streaming its actions back through the standard action path. Useful for debugging deterministic behavior.

## Training & data commands

### `train`

```bash
solarian train
```

Trains a policy from a recorded dataset using the configuration in `conf/train.yaml`. Supports ACT and diffusion policies (`model.type=act` or `model.type=diffusion`) and optional Weights & Biases logging.

### `dataset2lerobot`

```bash
solarian dataset2lerobot
```

Converts a Solarian-recorded dataset to the [LeRobot](https://github.com/huggingface/lerobot) on-disk format.

## Utility commands

### `detect-device`

```bash
solarian detect-device
```

Lists USB / serial devices currently connected to the host (port path and name). Handy when you need to fill in a `port:` field in a module config.

### `list-cameras`

```bash
solarian list-cameras
```

Detects and lists every camera available to the system (V4L2 on Linux, AVFoundation on macOS).

### `onshape-export`

```bash
solarian onshape-export <assembly_dir> [--clean-only] [--keys-file PATH] [--update-yaml PATH]
```

Exports an Onshape CAD assembly into an attachable MuJoCo (MJCF) model for [simulation](/docs/simulation). `<assembly_dir>` holds a `config.json` describing the assembly and a `solarian` block controlling the export. With `--update-yaml conf/<module>.yaml`, joint ranges from the cleaned MJCF are synced into that module conf's `sim_range_min`/`sim_range_max` and into `config.json` `joint_properties.*.limits`. See [Onshape → Sim Models](/docs/onshape-models) for the full workflow. Part of the `[sim]` extra.

### `shell`

```bash
solarian shell
```

Opens an IPython shell with `solarian.conf.settings` already loaded and your project on `sys.path`. Useful for poking at your `Robot`/`Controller` classes without spinning up the full pipeline.

## Authoring a custom command

Add a new file under `solarian/cli/commands/` (or your project's own command package) and register it with `CommandRegistry`:

```python
from omegaconf import DictConfig
from pydantic import BaseModel

from solarian.cli.base import BaseCommand, CommandRegistry


class MyCommandConfig(BaseModel):
    target: str
    speed: float = 1.0


@CommandRegistry.register('my-command')
class MyCommand(BaseCommand):
    help = "Run the my-command demo."

    def get_config_class(self):
        return MyCommandConfig

    def handle(self, cfg: DictConfig) -> None:
        print(f"Running {cfg.target} at speed {cfg.speed}")
```

To make the command discoverable without forcing an import on every CLI startup, register it lazily:

```python
CommandRegistry.register_lazy(
    "my-command",
    module_path="myproject.commands.my_command",
    help="Run the my-command demo.",
    config_name="my_command",          # picks conf/my_command.yaml
    setup_modules=("robot",),          # which project modules to auto-import
)
```

The command then runs as:

```bash
solarian my-command target=arm speed=2.0
```

If `config_name` is set, the command receives a parsed `DictConfig` from `conf/<config_name>.yaml`; otherwise it gets an empty `DictConfig`. If `get_config_class()` returns a Pydantic model, Solarian validates the config and prints friendly errors on failure.
