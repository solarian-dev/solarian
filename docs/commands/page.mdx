# Command Line Interface

Solarian ships two console scripts:

- **`solarian`** — the main CLI. Every project workflow (running a node, recording, training, …) goes through this command.
- **`create-solarian`** — a one-shot project scaffolder. See [Creating a Project](/docs/creating-a-project).

Run `solarian --help` to print the grouped command list.

## Global flags

Every `solarian` subcommand accepts these top-level flags before the subcommand name:

<Properties>
  <Property name="--conf" type="string">
    Path to the Hydra config directory. Defaults to <code>conf</code>. You can also pass <code>dir/name</code> to override the config name (for example, <code>--conf conf/robot_dev</code>).
  </Property>
  <Property name="--deployment, -d" type="string">
    Deployment profile in <code>conf/deployment/</code>, supplying the relay address and device ports for this host layout. Defaults to <code>$SOLARIAN_DEPLOYMENT</code>, then <code>localhost</code>. See <a href="/docs/project-configs#deployments">Deployments</a>.
  </Property>
  <Property name="--settings" type="string">
    Path to your project's <code>settings.py</code>. Auto-discovered when omitted (looks for <code>{`{package_name}`}/settings.py</code> based on <code>pyproject.toml</code>, then <code>conf/settings.py</code>).
  </Property>
  <Property name="--version, -V" type="flag">
    Print the installed Solarian version and exit. Works on its own, without a subcommand.
  </Property>
</Properties>

Hydra-style overrides on the command line (`key=value`) are forwarded to the underlying Hydra `compose()` call, so anything in your YAML can be overridden ad hoc.

```bash
solarian run-robot fps=60 connection.ip=192.168.1.20
```

Some commands also take parameters that are not YAML keys at all — `role`, `module`, `sweep`, `axis`. Hydra composes in struct mode and would normally reject those, so a command declares them in a `params` tuple and they are seeded before your overrides are applied:

```python
class CalibrateCameraLatencyCommand(BaseCommand):
    params = ("role", "monitor_hz", "qr_size", "n_frames", "plot", "allow_unsynced")
```

You then write them plainly, `role=display`, with no `+` prefix. A name that is neither a YAML key nor a declared parameter is still rejected, which is what catches `frps=60` before it silently does nothing.

## Project commands

### `create-project`

```bash
solarian create-project <project_name> [--force]
```

Scaffolds a new project. Prefer the standalone `create-solarian <name>` script — it's the same code, but works before a Solarian project exists in the current directory.

### `install`

```bash
solarian install <package-or-path>
```

Installs a plugin into the current Python environment, adds it to the project's `pyproject.toml`, and copies its config template into `conf/` when that file is not already there. A name is resolved on PyPI first (`ur5` installs `solarian-ur5`). If PyPI has no such project, the command looks in the current directory and then in `plugins/`. A path installs that directory editable and skips PyPI.

`templates/<folder>/<file>.yaml` is copied to `conf/<folder>/<file>.yaml`, so a module plugin's `templates/modules/ur5.yaml` lands at `conf/modules/ur5.yaml`, and the attribute on your `Robot` has to match that filename. See [Installing a plugin](/docs/plugins#installing-a-plugin) and [Project Configs](/docs/project-configs).

```bash
solarian install solarian-move
solarian install plugins/solarian-gripper1
solarian install ur5
```

### `create-plugin`

```bash
solarian create-plugin <type> <name> [--force]
```

Writes `solarian-<name>/` in the current folder: a pip package whose `pyproject.toml` entry points register the component, a stub to fill in, and an `AGENTS.md` for coding agents. `<type>` is `actuator`, `sensor`, `module`, `robot`, `command`, `policy` or `op`. Run it again with another type and the same name to add a second component to the plugin. See [Plugins](/docs/plugins).

```bash
solarian create-plugin actuator feetech
solarian create-plugin module feetech    # second component, same plugin
```

### `doctor`

```bash
solarian doctor [--json]
```

Checks the project or plugin in the current folder without importing it. It reports packages or `solarian-*` dependencies that are not installed, `settings.py` entries that name a missing class, robot modules without their `conf/modules/<name>.yaml`, deployment profiles that lack a `${deployment.*}` key the configs read, and agent files that are stale or were edited. Each problem comes with its fix. The command exits 1 when there is an error; `--json` prints the checks for a script or a coding agent.

### `agent`

```bash
solarian agent sync [--force]
solarian agent install [--target agents|claude|cursor] [--force]
```

`sync` regenerates `AGENTS.md`, `CLAUDE.md` and the skills under `.agents/skills` and `.claude/skills` for the installed Solarian and plugins. `create-project`, `create-plugin` and `install` run it for you. `install` copies the bootstrap skill into your user skill folders, so an agent finds Solarian from any folder. See [Using Solarian with coding agents](/docs/agents).

### `docs`

```bash
solarian docs [list | show <page> | search <term> | path]
```

Prints the docs that shipped with the installed Solarian as markdown, so they match the code. `list` prints every page's slug, title and summary; `show` prints one page, given its slug, `/docs/<slug>` or a solarian.dev URL; `search` prints the lines that contain a term.

```bash
solarian docs show skills
solarian docs search MOVE_L
```

### `add-op`

```bash
solarian add-op <name> [--force]
```

Writes `<package>/datasets/<name>.py`, a dataset op stub copied from the same template as the `drop_short_episodes.py` example every new project gets. Nothing needs registering: each file in `datasets/` is an op, named after the file with `_` turned into `-` (`split_by_success.py` is `split-by-success`), unless its class sets `name`. `--force` overwrites the file. See [Dataset ops](/docs/datasets#dataset-ops).

```bash
solarian add-op split-by-success
solarian dataset ops                 # lists it, with source project:arm1/datasets/split_by_success.py
```

## Robot commands

These commands run on the robot machine. They import the modules listed under <code>setup_modules=("robot", "observation", "action")</code>.

Every calibration command below opens its module in-process, not through the robot's action queues. Run it on the machine the device is wired to, with `run-robot` stopped, because a serial bus or a CSI camera can be open in one process only. The exception is `calibrate-camera-latency role=display`, which only draws on a screen. Each command writes what it measures into the module's own yaml, `conf/modules/<module>.yaml`.

The examples calibrate the Solarian Arm 1 project from the [real robot tutorial](/docs/tutorials/real-robot): the Feetech arm `right_arm`, the gripper `right_gripper` on the same bus, and the wrist camera `right_wrist_camera`, a Raspberry Pi camera from `solarian-picamera`. All three are wired to the Pi, so every command runs there with `-d pi`. Calibrate them in the order of the sections below. The arm comes first because the camera's last step moves the arm and trusts its joint calibration.

### `run-robot`

```bash
solarian run-robot
solarian run-robot --sim
solarian run-robot --sim --view
```

Loads `conf/robot.yaml`, instantiates your `Robot` subclass, spawns one process per `Module`, and starts the action receiver / observation publisher. See [Robots](/docs/robots). `--sim` runs the same robot in MuJoCo, in the `scene` its class declares, and `--view` adds a window that draws it; see [Simulation](/docs/simulation).

### Arm calibration

A new arm goes through these commands once, in this order. Afterwards, repeat only the step whose fact changed: `calibrate` after replacing a servo, and `calibrate-arm` after the arm's load or the module's `frequency` changes.

Example: `right_arm`, six Feetech servos on `/dev/ttyACM0`.

1. **Prepare each servo before it goes into the arm.** Connect one servo at a time to the bus adapter. Pick Feetech, the port and the servo, give it the ID its joint has in `conf/modules/right_arm.yaml`, and let the command park the shaft at mid-encoder. Fit the horn with the joint at mid-travel.

   ```bash
   solarian calibrate-servo
   ```

2. **Provision the assembled arm.** With every servo on the bus and the arm powered, pick `right_arm`. The module's `setup()` writes the IDs, baud rate and operating modes it needs onto the servos.

   ```bash
   solarian -d pi setup-module
   ```

3. **Record the joint limits, the home pose and the sim direction.** Pick `right_arm`. Move each joint through its full travel with torque off, match the sim's zero pose, then answer Y or N as each highlighted joint moves. This writes `real_range_min`, `real_range_max`, `center_offset` and `drive_mode` for every joint.

   ```bash
   solarian -d pi calibrate
   ```

4. **Check the spans against the model.** Every joint should print PASS. In the live mirror that opens afterwards, move the real arm and watch the sim follow it.

   ```bash
   solarian -d pi verify-calibration module=right_arm
   ```

5. **Measure speed and latency.** Pick `right_arm` and mode `all`. Free-drive the arm to each pose it asks for, then keep the volume clear while it ramps and sweeps. This writes `max_speed`, `max_joint_speed`, `action_latency` and `receive_latency`. A skill that moves the arm in Cartesian space needs these numbers; joint teleop does not.

   ```bash
   solarian -d pi calibrate-arm
   ```

The arm's calibration now lives in `conf/modules/right_arm.yaml`, and `run-robot` writes it onto the servos each time it connects. `write-robot-calibration` pushes it without starting the robot, and `derive-model-limits` is for whoever maintains the arm's MuJoCo model.

#### `calibrate-servo`

```bash
solarian calibrate-servo
```

Prepares one servo for use, before it is a module component: pick the brand, the port and the servo, then set its ID, reset the comms and position registers, and park the shaft at mid-encoder so you can fit the horn with the mechanism at mid-travel. Needs no project and no config.

Do this on every new servo. A horn fitted at an arbitrary shaft angle can put the `0/4095` encoder seam inside the joint's travel, which [Calibration](/docs/modules/calibration) has to reject — the servo cannot be commanded across the seam. The brand menu lists every installed actuator bus plugin; a brand whose plugin has no scanning support says so instead of failing.

#### `setup-module`

```bash
solarian setup-module
```

Lists the modules your `Robot` and `Controller` declare, connects the one you pick, and runs its `setup()` hook: the one-off provisioning a module plugin needs before the hardware can be used, such as writing actuator IDs, baud rates and operating modes. It writes to the device, not to the yaml. Run it once per new piece of hardware, before `calibrate`.

#### `calibrate`

```bash
solarian calibrate
```

Interactive bring-up for one module. Four steps on an IK arm: **Step 1: Joint limits**, **Step 2: Home position** (match the static model-q=0 sim), **Step 3: Sim mapping** (highlighted joint, Y/N), **Output**. The live mirror then stays open with on-screen nrm / rad numbers so you can check the mapping. Answer ENTER / Y / N in the sim window. Grippers stop after Step 1 plus one physical closed pose. See [Calibration](/docs/modules/calibration).

#### `verify-calibration`

```bash
solarian verify-calibration module=<attr>
```

Compares each joint's calibrated span (in radians) to the IK model's `jnt_range` and prints a per-joint PASS/FAIL table. On an arm it then opens the live sim mirror so you can move the real arm and confirm the sim tracks. See [Calibration](/docs/modules/calibration).

#### `calibrate-arm`

```bash
solarian calibrate-arm [axis=z] [amplitude=0.02] [freq=1.25] [poses=3] [distance=0.06]
```

Measures the three numbers that describe an `ArmModule` in time, and writes each into the arm's module yaml as it goes. You pick the arm (auto-selected when there is only one) and a mode:

- **all** — the three below, in order.
- **speed** — at rising speeds from several poses: short moves along x, y and z → `max_speed[0]`; turns of the tool about x, y and z → `max_speed[1]`; a swing of each joint → `max_joint_speed`.
- **action** — sweep a Cartesian sinusoid on one axis, record the measured pose, and recover the command-to-motion delay by cross-correlation → `action_latency`. Shows alignment plots.
- **obs** — time a few hundred pose reads and report the mean → `receive_latency`. On a bus that answers reads from cached motor replies, such as Robstride, it measures how old each reading is instead, with the control loop ticking.

The order in `all` is the point of merging them. The sinusoid's peak velocity has to stay inside `max_speed`, because `PoseTrajectoryInterpolator` stretches any waypoint it cannot reach in time and a stretched sweep measures the speed limit rather than the pipeline — so the speed is measured first and `amplitude` is shrunk to fit the result. Run `all` on new hardware; the individual modes are for re-measuring one number later.

A negative latency means the sweep did not track, and is not written.

Speed mode free-drives the arm to each pose in turn, through take-hold / release-torque / lock / let-go prompts. For each of the three speeds, the first sample ramps the commanded speed until the measured motion stops keeping up, and every later pose, direction and joint is checked against that speed, lowering it whenever one cannot hold it. Between samples the arm drives back to the pose you chose rather than reversing the offset it just made, so a move that fell short does not shift where the next one begins. What it reports is the slowest sample, since the Jacobian means a single global limit is only safe if it is the minimum over the region the arm works in. Directions, turns and joints without room for the full test move are skipped rather than measured short.

The moves deliberately run above the configured limits — that is the only way to see past them — up to four times the configured value. For the length of the ramps the command lifts `max_speed`, `max_joint_speed`, `max_accel` and `max_joint_accel`, and with them the motors' own speed cap, then puts them back. If the arm keeps up all the way to the ceiling, the ceiling is written: the arm has shown it holds that speed, and running speed mode again climbs up to four times further.

`max_joint_speed` holds Cartesian moves too: a `moveL` whose path would need a faster joint is slowed as a whole, and a streamed `servoL` / `scheduleL` falls behind rather than off its path. A module whose motors take a speed cap of their own (the Robstride arms and grippers) sets it to 1.5 times the planned speed, so no planned move reaches it and a bad target or a wrong calibration does.

Action mode asks for one more placement, then verifies the model can travel the full amplitude both ways from that pose and aborts naming the joint in the way, because an out-of-reach sweep comes back clipped and the clip is what gets measured. The arm returns to where it was when the command started, including when the run aborts partway. See [Latency & Synchronization](/docs/latency) for what each number corrects and why.

#### `write-robot-calibration`

```bash
solarian write-robot-calibration
```

Writes the calibration values listed in your YAML into the actuators / sensors themselves (e.g. servo offsets stored on the device EEPROM). Re-pushes an existing [calibration](/docs/modules/calibration) file without re-sweeping.

#### `derive-model-limits`

```bash
solarian derive-model-limits module=<attr> [sweep=true]
```

Prints MJCF-ready joint `range="lo hi"` values (radians) derived from the real arm's mechanical limits — from the existing calibration, or a guided live sweep with `sweep=true`. For model authors keeping `jnt_range` equal to the real hard-stops. See [Calibration](/docs/modules/calibration).

### Gripper calibration

A gripper needs three facts: the servo's travel, how far the jaws actually open at each point of it, and how fast and how late they respond.

Example: `right_gripper`, one Feetech servo on the same bus as `right_arm`.

1. **Record the travel and the closed pose.** Pick `right_gripper`. Open and close the jaws by hand through their full travel, then hold the fingers together and confirm. A gripper skips the arm's home and direction steps.

   ```bash
   solarian -d pi calibrate
   ```

2. **Measure the opening against a ruler.** Pick `right_gripper` and accept the default number of stops. At each stop, measure the gap between the fingertips and type it in millimetres. The pairs are saved as `aperture_table`, so a commanded opening of 40 means 40 mm.

   ```bash
   solarian -d pi calibrate-gripper-ranges
   ```

3. **Measure speed and latency.** Pick `right_gripper` and mode `all`. Keep fingers out of the jaws while it strokes. This writes `max_speed`, `action_latency` and `receive_latency`.

   ```bash
   solarian -d pi calibrate-gripper
   ```

#### `calibrate-gripper-ranges`

```bash
solarian calibrate-gripper-ranges
```

Sweeps the servo across its normalized range and asks you for a ruler reading (mm) at each stop, then writes the pairs to `aperture_table` in the module yaml (UMI `calibrate_gripper_ranges`). That table is what `GripperModule` interpolates to turn a commanded aperture into a servo value. Without it the module assumes the opening is a straight line between `aperture_closed_mm` and `aperture_open_mm`, which a parallel gripper's linkage does not follow.

#### `calibrate-gripper`

```bash
solarian calibrate-gripper [amplitude=8] [freq=1.25]
```

The same four modes for any `GripperModule` (UMI `calibrate_gripper_latency`, plus the speed ramp UMI had no equivalent for), writing `max_speed`, `action_latency` and `receive_latency` into the gripper's module yaml.

The gripper's speed is a genuine hardware constant: one prismatic degree of freedom, no Jacobian, so a single measurement holds everywhere. It strokes between the ends of travel (staying a tenth clear of the hard stops) at rising speed and reports the rate the jaws hold, along with whether the configured value was optimistic, pessimistic, or fair. The configured value is only where the ramp starts: it climbs until the jaws fall behind, lifting the motor's own speed cap while it runs. The one ceiling is timing. A stroke spans fewer control ticks the faster it goes, so the ramp stops once its middle 80% would take under five ticks at the module's `frequency`. If the jaws are still keeping up there, that speed is written as a floor, and a higher `frequency` measures further.

Getting this order wrong is not hypothetical. UMI swept the full stroke at about 1 Hz, which peaks at 300 mm/s — fine for the WSG50 they ran, twice what a 150 mm/s gripper can follow. Run that sweep against the smaller gripper and every waypoint is stretched, the jaws crawl, and the cross-correlation returns a lag with no physical meaning. The sweep now sizes itself from `max_speed` and refuses an explicit `amplitude`/`freq` pair that would exceed it.

### Camera calibration

A camera that a [UMI](/docs/tutorials/skills/umi) policy reads needs three calibrations: its lens, its delay, and where the fingertips sit in its frame. A camera that you only watch needs none of them.

Example: `right_wrist_camera`, an IMX477 with a fisheye lens on the Pi's CSI connector 0. The windows these commands open need a display on the Pi, or an `ssh -Y` session.

1. **Find the camera.** Check that the Pi camera is listed, and note its index.

   ```bash
   solarian -d pi list-cameras
   ```

2. **Calibrate the lens onto GoPro optics.** Print the <a href="https://github.com/opencv/opencv/blob/master/doc/pattern.png" target="_blank" rel="noreferrer">OpenCV 9x6 checkerboard</a> flat on stiff card. Pick the camera's index, then hold the board in front of it in at least 8 different positions and tilts. The command saves `conf/calibrations/right_wrist_camera_gopro_remap.json` and sets `optical_remap` in the camera's yaml. Then it opens an overlay against UMI's reference image, which is how you aim the camera on its mount. Open the gripper to about 80 mm before tracing the finger pads, since the pads' place in the frame moves with the opening. Run it again with `overlay_only=true` whenever you re-aim the camera.

   ```bash
   solarian -d pi calibrate-umi-camera camera_yaml=right_wrist_camera
   ```

3. **Measure the camera's delay.** Start the relay with `run-server` if it is not running, since both sides sync their clocks to it. Show the QR code on the Mac's monitor, and point the camera at that monitor from the Pi. Pick `right_wrist_camera`, and set `monitor_hz` to the monitor's refresh rate. The result corrects `receive_latency` rather than replacing it, so run the capture again until the residual it reports is close to zero.

   ```bash {{ title: 'On the Mac' }}
   solarian -d pi calibrate-camera-latency role=display monitor_hz=60
   ```

   ```bash {{ title: 'On the Pi' }}
   solarian -d pi calibrate-camera-latency role=capture monitor_hz=60
   ```

4. **Measure where the fingertips sit in the camera frame.** Print UMI's <a href="https://umi-gripper.github.io/share/table_marker.pdf" target="_blank" rel="noreferrer">table marker</a> at 100 percent, tape it flat in reach of the arm, and measure the black square: pass `marker=<mm>` if it is not 160 mm. Pick `right_wrist_camera`, set one pose by hand with the tag in view, and let the arm orbit the tag. The result is saved to `conf/calibrations/right_wrist_camera_hand_eye.json`. The command prints a rotation to paste into the arm's `ik_tcp`, and a translation that tells you how far to move the camera mount.

   ```bash
   solarian -d pi calibrate-hand-eye arm=right_arm
   ```

#### `calibrate-umi-camera`

```bash
solarian calibrate-umi-camera [camera_yaml=<module>] [overlay_only=true] [images=<dir>]
```

From the `solarian-umi` plugin. Fits a fisheye model to checkerboard captures from a connected camera and remaps it onto the GoPro Hero 10 with Max Lens Mod that UMI policies were trained on. It writes `conf/calibrations/<module>_gopro_remap.json`, points the camera yaml's `optical_remap` at it, and sets the yaml's `resize_width` and `resize_height` to 640x360. Then a live overlay against UMI's reference image shows whether the fingers, holders and screws land where a policy expects them. Hold the gripper at an opening of about 80 mm while you trace the overlay, because the solved rotation would otherwise absorb a difference in jaw width as camera tilt. `camera_yaml` names the camera to write into. Without it, the command writes into the camera of `conf/skills/umi.yaml`, so name it when the project has more than one camera. `overlay_only=true` skips straight to the overlay, and `images=` reuses an earlier capture. It does not need `run-server` or `run-robot`, and both must be stopped because they hold the camera.

#### `calibrate-camera-latency`

```bash
# on the machine with a monitor
solarian calibrate-camera-latency role=display [monitor_hz=60] [qr_size=720]

# on the robot, camera pointed at that monitor
solarian calibrate-camera-latency role=capture monitor_hz=60 [n_frames=120] [plot=true]
```

Measures the camera's `receive_latency` with UMI's QR-timestamp method, and writes it to the camera module's yaml: one role fills a screen with a QR code encoding the instant it was drawn, the other films it and subtracts. `monitor_hz` is required on `capture`, where display refresh enters the arithmetic, and optional on `display`, where it only paces the redraw. Both roles sync to the relay clock, so the screen and the camera can be on different machines — which is the better setup, though both can share one machine if the robot has a screen. See [Latency & Synchronization](/docs/latency).

#### `calibrate-hand-eye`

```bash
solarian calibrate-hand-eye [arm=<module>] [marker=160] [tag=13] [mode=auto|manual] [joints=fit]
```

Measures the rigid transform from the wrist camera to the fingertips, which a UMI policy assumes and can never observe. Tape UMI's table marker flat and leave it there: it is the fixed world frame of the solve. In `mode=auto` (the default) you set one anchor pose by hand and the arm orbits the tag by itself. `mode=manual` has you pose every sample. `marker` is the measured side of the black square in mm and sets the scale of the answer. The result is saved to `conf/calibrations/<camera>_hand_eye.json`. It splits into a rotation, printed as a quaternion for the arm's `ik_tcp`, and a translation, which no config can absorb and which is an instruction for the camera mount. `joints=fit` also measures the arm's joint zeros from the same sweep. Needs an arm with an `ik_tcp`, and a camera that `calibrate-umi-camera` has already calibrated.

## Controller commands

These run on the controller machine. They import <code>setup_modules=("controller", "observation", "action")</code>.

### `run-controller`

```bash
solarian run-controller
```

Loads `conf/controller.yaml`, instantiates your `Controller` subclass, and starts the action sender / observation receiver. See [Controllers](/docs/controllers).

### `calibrate-controller`

```bash
solarian calibrate-controller
```

Runs controller-side calibration. Used for leader-arm setups where the *controller* hardware also needs zeroing.

### `write-controller-calibration`

```bash
solarian write-controller-calibration
```

Writes the calibration values from YAML into the controller hardware.

### `run-server`

```bash
solarian run-server
```

Starts a [`RelayServer`](/docs/servers) using `conf/server.yaml`. Run this on the relay machine — typically a small box on the same network as both the robot and the controller.

## Services commands

A [service](/docs/services) is a model that skills call over HTTP, such as a tracker, a depth model or a policy server. Run it on the machine with the GPU, which need not be the robot or the controller.

### `run-service`

```bash
solarian run-service <conf_or_service> [--checkpoint PATH] [--host HOST] [--port PORT] [server args...]
```

Runs a [service](/docs/services): a tracker, a depth model, or a [policy](/docs/policies) server. Name a conf in `conf/services/` or `conf/skills/` with a `server:` block to run the server it describes, with its checkpoint, port and args, or name an installed service to run it with your own. `--checkpoint`, `--host` and `--port` override the conf, and every other argument goes to the server after the conf's `args`. So `solarian run-service bbox_tracker` starts the SAM 2 tracker `conf/services/bbox_tracker.yaml` calls, `solarian run-service umi_target --checkpoint models/pick/checkpoints/latest.ckpt` the diffusion policy `conf/skills/umi_target.yaml` drives, and `solarian run-service sam2-tracker --model small` the tracker with your arguments. An unknown name lists the installed services. To serve on Solarian Base's GPUs instead, see [Services, Policies & Models](/docs/solarian-base/endpoints).

## Recording commands

### `record`

```bash
solarian record num_episodes=10 episode_time_s=20
```

The same teleop loop as `run-controller`, cut into episodes: reset the scene, record for `episode_time_s`, seal, repeat. Press `delete` during an episode to throw it away and record it again — the index is reused, so a bad take leaves no gap — `r` to seal early, and quit the UI to end the session.

`conf/commands/record.yaml` holds only the shape of the session (`name`, `num_episodes`, `episode_time_s`, `reset_time_s`, `tasks`). The `recording:` block in `conf/controller.yaml` picks which sides record: the robot, into `recordings/robot/`, and the controller, into `recordings/controller/`. The robot's `conf/robot.yaml` `recording:` block holds how the robot stores its episodes. The command refuses to start when neither side would record. See [Recording](/docs/recording).

## Training & data commands

### `export-dataset`

```bash
solarian export-dataset recordings/robot/0003_7f3a9c_cup_stacking
```

Turns a recorded session — archive mp4s plus one parquet per episode, all at native rates — into a LeRobot v2.1 dataset: every signal resampled onto one grid, every frame warped through the camera's optical remap and downscaled to the observation resolution. The session is never modified, so recalibrate a camera or change your mind about the rate and export again from the same recording. `--fps`, `--episodes A,B,C`, `--no-remap` and `--overwrite` cover the rest. See [Recording](/docs/recording).

### `dataset`

```bash
solarian dataset ops [--json]
solarian dataset new <source> <dir>
solarian dataset apply <dir>[@VERSION] <op> [--param KEY=VALUE]... [--review | --online]
solarian dataset log <dir>
```

Runs [dataset ops](/docs/datasets#dataset-ops) on recorded sessions without changing them. `new` starts a computed dataset over a session; `apply` adds a version made by an op on another version (by default the only leaf, or `@source`). `redo`, `accept`, `close`, `drop`, `export` and `rebuild` cover the rest, and `solarian dataset --help` lists them all. `--project DIR` picks the project whose `datasets/` load, by default the one around the current directory.

### `umi-slam`

```bash
solarian umi-slam datasets/cup_session
```

Turns a directory of GoPro or Lumi collector MP4s into `dataset.zarr.zip` for UMI training. This is not a `solarian record` session. ORB-SLAM3 runs in Docker image `chicheng/orb_slam3:latest` and GoPro IMU extraction in `chicheng/openicc:latest`. If an image is not already on this machine, the command asks before downloading it. The copied pipeline is from [Universal Manipulation Interface](https://github.com/real-stanford/universal_manipulation_interface) (MIT). Add the dataset it writes to `task.dataset_mix` in a training file, `conf/training/<name>.yaml`. See [Training](/docs/training).

### `train`

```bash
solarian train --conf conf/training/cup_arrange
```

Runs one training file with the trainer its `trainer:` key names. There is no default file. A trainer plugin seeds `conf/training/<name>.yaml` on install; copy that file per run. For UMI (`trainer: umi`), each copy writes `models/<job_name>/checkpoints/latest.ckpt`, and the same `UMISkill` loads that checkpoint from the matching skill yaml. See [Training](/docs/training).

From the `solarian-base` plugin. ### `cad-import`

```bash
solarian cad-import <assembly_dir>
solarian cad-import <assembly_dir> --urdf download.zip
solarian cad-import <assembly_dir> --clean-only
solarian cad-import <assembly_dir> --density 522
```

Reads a URDF and the meshes a CAD tool already wrote to disk, and cleans them into an attachable MuJoCo model for [simulation](/docs/simulation). Nothing is fetched from a CAD server. The model name is `<assembly_dir>` with `_description` removed (`gripper1_description` writes `../gripper1.xml`, `gripper1_raw.xml`, and `meshes/`). The first import writes `config.yaml` in that directory; later imports keep your edits to it. `--density` overrides the file's density for one run.

```text
<assembly_dir>/
  robot.urdf          # or urdf/robot.urdf
  meshes/*.stl
```

Name mates `dof_<name>` (an actuated joint `<name>`; `dof_<name>_inv` flips the axis), frames `frame_<name>` (`frame_flange`, `frame_tcp`, `frame_camera` become sites `flange`, `tcp`, `camera`), fastened parts `fix_<name>`, link overrides `link_<name>`, and loop closures `closing_<name>`. The prefix is removed in the MJCF. A name containing `wheel` or `continuous` is a joint with no limits. A `<mimic>` follower gets no actuator.

- **Onshape.** Right-click the assembly tab, Export, format URDF, geometry STL, and uncheck "Export rigid subassemblies as a single link". It downloads a zip file that contains the URDF and the meshes. You can reference it in the command like this: `solarian cad-import <assembly_dir> --urdf download.zip`.
- **FreeCAD.** The RobotCAD workbench exports a URDF package. Meshes as STL, in meters.
- **Blender.** The Phobos add-on, mesh format STL.
- **SolidWorks.** SW2URDF writes `urdf/<robot>.urdf` and `meshes/`. Set the mesh format to STL; the package folder can be the assembly directory.

`--density` overrides the `config.yaml` density for that run and does not rewrite the file. Module yamls hold no joint limits; the sim reads them from the MJCF. See [Models from CAD](/docs/simulation#models-from-cad) for the click-by-click export. Part of the `[sim]` extra.

## Authoring a custom command

Add a new file under `solarian/cli/commands/` (or your project's own command package) and register it with `CommandRegistry`:

```python
from omegaconf import DictConfig
from pydantic import BaseModel

from solarian.cli.base import BaseCommand, CommandRegistry


class MyCommandConfig(BaseModel):
    target: str
    speed: float = 1.0


@CommandRegistry.register('my-command')
class MyCommand(BaseCommand):
    category = "Robot"
    help = "Run the my-command demo."

    def get_config_class(self):
        return MyCommandConfig

    def handle(self, cfg: DictConfig) -> None:
        print(f"Running {cfg.target} at speed {cfg.speed}")
```

`category` is the heading `solarian --help` lists the command under. Set `uses_config = False` when the command does not read a project yaml (no `settings.py`, and the global `--conf` / `--deployment` flags are hidden from its help).

A command that takes positionals or flags implements `parse_args`. It stores what it parsed on `self`, returns `[]`, and `handle` reads those attributes. The default returns the argv unchanged, and Hydra composes those tokens as `key=value` overrides.

To make the command discoverable without forcing an import on every CLI startup, register it lazily. Repeat `help` and `category` here: the command list is built from this record, so it can group commands without importing the module.

```python
CommandRegistry.register_lazy(
    "my-command",
    module_path="myproject.commands.my_command",
    help="Run the my-command demo.",
    config_name="commands/my_command", # picks conf/commands/my_command.yaml
    setup_modules=("robot",),          # which project modules to auto-import
    category="Robot",
)
```

The command then runs as:

```bash
solarian my-command target=arm speed=2.0
```

If `config_name` is set, the command receives a parsed `DictConfig` from `conf/<config_name>.yaml` (`commands/record` is `conf/commands/record.yaml`); otherwise it gets an empty `DictConfig`. If `get_config_class()` returns a Pydantic model, Solarian validates the config and prints friendly errors on failure.
