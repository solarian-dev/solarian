# Adding a New Arm

Solarian mirrors the UMI / UR5 control pattern for any MinkIK arm: controllers and skills send **sparse, timestamped Cartesian waypoints**; the arm **module** upsamples them with a `PoseTrajectoryInterpolator` at its control rate and the [`IKActuatorBus`](/docs/ik) turns each pose into joint targets. The only arm-specific piece is the kinematics (MJCF + `MinkIK` + joint mapping). {{ className: 'lead' }}

```text
Controller / skill  (~10–30 Hz)
        │  SCHEDULE_L  x,y,z,rx,ry,rz + wall-clock timestamp
        ▼
Arm Module  (frequency: 90, interpolator_type: pose)
        │  PoseTrajectoryInterpolator sample @ module rate
        │  write x..rz
        ▼
IKActuatorBus (Mink differential IK)
        │
        ▼
Joint bus (Feetech / sim BusClient)
```

On a UR5, UMI streams dense TCP poses with `servoL` and the robot controller does IK. Here there is no onboard Cartesian servo, so **host IK** replaces that step — the interpolator API stays the same.

## Contract

A new arm reuses the core path when it provides:

1. **Joint servos** — hardware actuators the IK bus will write.
2. **Six `CartesianIKActuator`s** — `x`, `y`, `z`, `rx`, `ry`, `rz` with `cfg.id` 0..5 and `mode: raw`.
3. **`ik_backend = MinkIK(...)`** — MJCF, joint-actuator → MuJoCo joint map, TCP frame.
4. **Yaml** — `interpolator_type: pose`, `max_speed: [max_pos_m_s, max_rot_rad_s]`, and a module `frequency` higher than the controller (e.g. 90 Hz).
5. **Callers** — emit `ActionType.SCHEDULE_L` with pose fields and wall-clock `timestamp` for policy chunks (absolute target times minus action latency). Teleop uses `MOVE_L`; leader follow uses `SERVO_J`.

No per-arm interpolator code. Optional extras: servo gains in `initialize()`, and `default_joint_speed` if 1.05 rad/s is the wrong `moveJ` limit for this arm.

## Example: SO-106

The `so106` project arm is the reference implementation.

### Module class

Declare joints, Cartesian axes, and MinkIK. Pose scheduling / sampling is inherited from [`Module`](/docs/modules) when yaml sets `interpolator_type: pose`:

```python
from solarian.core.module import Module
from solarian_feetech.actuator import FeetechServo
from solarian.core.ik import CartesianIKActuator, MinkIK

IK_JOINT_ACTUATORS = [
    "shoulder_pan", "shoulder_lift", "elbow_flex",
    "wrist_flex", "wrist_yaw", "wrist_roll",
]

class ArmModule(Module):
    shoulder_pan = FeetechServo()
    shoulder_lift = FeetechServo()
    elbow_flex = FeetechServo()
    wrist_flex = FeetechServo()
    wrist_yaw = FeetechServo()
    wrist_roll = FeetechServo()

    x = CartesianIKActuator()
    y = CartesianIKActuator()
    z = CartesianIKActuator()
    rx = CartesianIKActuator()
    ry = CartesianIKActuator()
    rz = CartesianIKActuator()

    ik_backend = MinkIK(
        mjcf="assets/so106.xml",
        joints=dict(zip(IK_JOINT_ACTUATORS, IK_JOINT_ACTUATORS)),
        frame="tcp",
        position_cost=1.0,
        orientation_cost=1.0,
    )
```

When the TCP is a CAD Frame on the gripper, pass that tool's flange-relative pose into the arm (`So106ArmModule(ik_tcp=UmiSlimFeetechModule.tcp_from_flange)`). MinkIK tracks the arm `flange` and applies the offset. Named poses a skill can drive live in `conf/skills/move.yaml`.

### Arm yaml

```yaml
# conf/modules/right_arm.yaml
frequency: 90
interpolator_type: pose
max_speed: [0.25, 0.6]   # m/s, rad/s (UMI-like)

actuators:
  shoulder_pan: { id: 1, port: ${actuator_port}, sim_joint: "right/shoulder_pan", ... }
  # ... remaining joints ...
  # cartesian x..rz are omitted — id comes from the attribute name, mode is raw
```

`frequency` is the upsample / IK rate. Controllers stay at ~30 fps and only carry sparse setpoints.

### Scheduling a waypoint (teleop)

Match UMI SpaceMouse teleop: advance the absolute target locally, then schedule **one controller period ahead**:

```python
from solarian.core.action import Action, ActionType

target_time = time.time() + 1.0 / controller_fps
data = {
    axis: {"value": float(pose[i]), "timestamp": target_time}
    for i, axis in enumerate(("x", "y", "z", "rx", "ry", "rz"))
}
arm_action = {"action_type": ActionType.SCHEDULE_L, "data": data}
return Action(
    action_type=ActionType.MODULE_ACTION,
    data={"right_arm": arm_action},
)
```

The module converts wall time → monotonic, inserts the waypoint with speed limits, and each `control_step` writes the interpolated pose through IK.

### Policy / skill path

Skills should **not** own a second arm `PoseTrajectoryInterpolator` (that double-smooths). Forward each predicted pose with its absolute `target_time` (minus the arm module's [`action_latency`](/docs/latency)) as `SCHEDULE_L` on the arm module — same as UMI `exec_actions` → `schedule_waypoint` on the RTDE controller.

### Robot + scene

Wire the module on the [`Robot`](/docs/robots), expose pose fields on [`Action`](/docs/actions) / [`Observation`](/docs/observations), and attach the MJCF in a [`Scene`](/docs/scenes) (sim). Real and sim share the same module yaml; only `sim_joint` / `sim_range_*` differ.

## Checklist for a new arm

- [ ] MJCF with correct joint names and end-effector site/body
- [ ] Module: joint servos + six `CartesianIKActuator`s + `MinkIK`
- [ ] Yaml: `interpolator_type: pose`, `max_speed`, `frequency`; cartesian x..rz omitted from yaml
- [ ] Action / observation schemas include `x..rz`
- [ ] Controllers / skills use `SCHEDULE_L` with wall-clock timestamps
- [ ] [Calibration](/docs/modules/calibration) so real hardware tracks Cartesian moves
