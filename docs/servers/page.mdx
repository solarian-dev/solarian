# Server

The **RelayServer** is the middle node in Solarian's three-node architecture. It runs anywhere reachable from both ends and is responsible for: {{ className: 'lead' }}

- Receiving [Actions](/docs/actions) from controllers and forwarding them to the robot.
- Receiving [Observations](/docs/observations) from the robot and forwarding them to all subscribed controllers.
- Optionally running **server-side observation processors** — `CalculatedField`s with `computer=DataComputer.SERVER` (e.g. tracking, depth estimation) that augment observations *before* they reach the controller.
- Handling lightweight side-channel events from controllers, like click points and stop-tracking signals.

Defined in [`solarian/core/server.py`](https://github.com/solarian-dev/solarian/blob/main/solarian/core/server.py).

## Why a relay?

Decoupling the controller from the robot lets you:

- Run them on different networks or machines without each side having to know the other's address.
- Drop, swap, or add controllers (teleop, policy, recorder) without touching the robot loop.
- Compute expensive observation enrichments (vision models, tracking) on a beefier machine than the robot itself.
- Provide a single, stable bind address that all participants connect to.

## Defining a Server

The framework provides `RelayServer`. Most projects subclass it and leave it empty:

```python
from solarian.core import RelayServer

class MyServer(RelayServer):
    pass
```

Override methods only when you need to add custom behavior on top of the relay (custom event handling, logging, metrics).

## Registering your Server class

Set `SERVER_CLASS` in your project's [`settings.py`](/docs/settings):

```python
SERVER_CLASS = 'myrobot.server.MyServer'
```

`solarian run-server` reads this, imports the class, and instantiates it with the parsed `ServerConfig` from `conf/server.yaml`.

## ZMQ topology

The relay opens four ZeroMQ sockets and binds all of them. The robot and the controllers *connect* to the relay — never to each other.

```text
Controller (PUSH)  ──────►  action_receiver_port  ┐
                                                  │
                                              RelayServer  ──►  action_sender_port  (PUSH) ─► Robot (PULL)
                                                  │
Controller (SUB) ◄──────  state_sender_port    ◄──┘
                                                                                     ▲
                                              RelayServer ◄── state_receiver_port  ◄─┘  Robot (PUB)
```

The relay binds to `tcp://*:<port>` on all four ports. The robot and controllers each connect to `tcp://<server_ip>:<port>` using their respective port from the `ConnectionConfig`.

<Properties>
  <Property name="action_receiver_port" type="int">
    Port the controller pushes actions to. The relay binds a <code>PULL</code> socket here.
  </Property>
  <Property name="action_sender_port" type="int">
    Port the robot pulls actions from. The relay binds a <code>PUSH</code> socket here.
  </Property>
  <Property name="state_receiver_port" type="int">
    Port the robot publishes observations to. The relay binds a <code>SUB</code> socket here.
  </Property>
  <Property name="state_sender_port" type="int">
    Port controllers subscribe to for observations. The relay binds a <code>PUB</code> socket here.
  </Property>
</Properties>

All four sockets use `ZMQ_CONFLATE=1`, which keeps only the most recent message in the queue. Robot control prefers freshness over backlog: if a controller pauses for a tick, the next observation it receives is the latest one, not a stale one.

## Configuration

Default `conf/server.yaml`:

```yaml
connection: ${deployment.connection}

img_compression_quality: 70
```

`conf/robot.yaml` and `conf/controller.yaml` say the same thing, so all three roles read one `connection` block from the active [deployment](/docs/project-configs#deployments) at `conf/deployment/localhost.yaml`:

```yaml
connection:
  ip: 127.0.0.1
  action_sender_port: 5555
  action_receiver_port: 5556
  state_sender_port: 5557
  state_receiver_port: 5558
  clock_sync_port: 5559
```

For a multi-machine setup, add `conf/deployment/lab.yaml` with the relay machine's IP and launch each of the three nodes with it:

```bash
solarian run-server --deployment lab       # on the relay machine
solarian run-robot --deployment lab        # on the robot
solarian run-controller --deployment lab   # on the laptop
```

All three nodes need to agree on the same four port numbers and the same relay IP, which is why they share one deployment file rather than each carrying its own copy.

## Server-side observation processors

[`CalculatedField`](/docs/observations) declarations on your `Observation`/`ModuleObs` schema can specify *where* they run via `computer=DataComputer.SERVER`. When the relay starts, it instantiates one processor per such field via `Observation.create_processors(DataComputer.SERVER)` and runs them in the state-relay loop:

```python
from solarian.core.observation import CalculatedField, ModuleObs
from solarian.core.data import DataComputer, BoundingBoxData

class CameraObs(ModuleObs):
    rgb = SensorField(MyRobot.cam.sensor.rgb_image)
    bbox = CalculatedField(
        inputs=[MyRobot.cam.sensor.rgb_image],
        processor=BBoxProcessor,
        computer=DataComputer.SERVER,    # runs on the relay, not the robot
        output=BoundingBoxData(),
        conf="conf/bbox.yaml",
    )
```

The processor receives every incoming observation, computes its output, and the relay merges the result back into the message before it goes out to controllers. This is how Solarian keeps heavy CV workloads off the robot while still exposing them as first-class observation fields.

## Side-channel events

Controllers can also send lightweight non-action messages through the action socket. The relay recognizes two of them and dispatches `on_event(...)` calls to every server-side processor:

- `click` — used by tracking processors to seed a track from a UI click. The relay also stamps the next outgoing observation with a matching `click_ack`.
- `stop_tracking` — tells trackers to release.

You generally don't interact with these directly; they're used by the controller's display loop and bounding-box overlays.

## Running the server

From the project directory on whichever machine you've designated as the relay:

```bash
solarian run-server
```

The relay binds the four ports and starts the action-relay and state-relay threads. Logs print one line per forwarded message at debug level.
