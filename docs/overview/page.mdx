# Overview

**Solarian** is an open-source Python framework for building, controlling, teleoperating, and training robots. It gives you a clean three-node architecture, real-time multi-process modules, plug-and-play hardware and skills, and an AI agentic controller that drives the robot from plain-language chat with any vision-language model — all configured with [Hydra](https://hydra.cc/) and connected over [ZeroMQ](https://zeromq.org/). {{ className: 'lead' }}

Solarian sits between your hardware and your application code. ## Architecture

Solarian is structured as a **Robot ↔ Server ↔ Controller** system. Each role is a separate process and can run on a separate machine.

<ArchitectureFigure />

Zoomed in, each node is itself a set of processes and threads. On the robot, every module runs in its own process at its own rate and trades observations and actions with the robot loop through shared-memory ring buffers and queues. Skills run as their own processes or threads on the robot or the server, and policy-driven skills call a policy server. On the controller, the AI agentic controller plans the task with a vision-language model and starts skills as tools, while the controller loop records observations and merges teleop and skill actions into the `Action` it sends.

<ArchitectureExtendedFigure />

- **Robot** runs on the robot. It owns the hardware: every `Module` subclass becomes its own OS process, polls actuators and sensors, and streams typed observations back out. Implementation: [`solarian/core/robot.py`](https://github.com/solarian-dev/solarian/blob/main/solarian/core/robot.py).
- **RelayServer** runs anywhere reachable from both ends. It forwards actions from controllers to robots and observations from robots to controllers, and can run server-side observation processors. Implementation: [`solarian/core/server.py`](https://github.com/solarian-dev/solarian/blob/main/solarian/core/server.py).
- **Controller** decides what the robot should do next. Subclass `Controller` for keyboard teleop, leader-arm teleop, a learned policy, or add an `agent:` block to turn it into an AI agent that takes tasks from a chat, plans them with a vision-language model, and runs your skills as tools. Implementation: [`solarian/core/controller.py`](https://github.com/solarian-dev/solarian/blob/main/solarian/core/controller.py).

All three nodes speak the same protocol: a Pydantic-validated [`Action`](/docs/actions) goes one way, a Pydantic-validated [`Observation`](/docs/observations) comes the other. Both are msgpack-serialized over ZeroMQ.

## Vision

Solarian's vision is to **standardize the architecture of a robotics project**, so the next robot reuses what the last one already proved. Hardware modules, policies, models, and skills share one set of interfaces. A Feetech arm and a UR5 are both a `Module`. A keyboard teleop session and a learned policy consume the same `Observation` and produce the same `Action`. A `Skill` written for one robot runs on another that exposes the same `ModuleAction`.

Those interfaces hold classical control and learned policies together. Inverse kinematics, waypoints, and teleoperation run alongside a diffusion policy or a vision-language model, reading one observation stream and writing one action stream. A project combines them because they already agree on the types.

New functionality ships as a plugin instead of landing in one monolithic repository. A driver, a skill, or a policy is its own package, and a project installs the ones it needs. What stays in the project is small and obvious — a few classes and a `conf/` tree — and flexible.


## Key features

- **Real-time multi-process modules.** Each hardware [`Module`](/docs/modules) runs in its own process at its own configurable rate (`frequency` Hz), talking to the robot loop through shared-memory ring buffers, so a 500 Hz arm and a 30 Hz camera coexist without blocking each other. Scheduling is a property, not a base class, so cheap input devices like a keyboard run inline instead of paying for a process.
- **Typed observations and actions.** [`Observation`](/docs/observations) and [`Action`](/docs/actions) are Pydantic-typed schemas that bind directly to your modules. The same data flows from hardware through the wire to your controller, your dataset, and your policy.
- **Plug-and-play hardware and skills.** Both ship as standalone [plugins](/docs/plugins). `solarian install ur5` installs the hardware driver and copies its config into `conf/modules/ur5.yaml`. `solarian install move-skill` installs the skill and copies its config into `conf/skills/move.yaml`.
- **AI Agentic Controller.** Agentic control for any robot. [Any controller](/docs/agentic_controller) can wrap a vision-language model (Anthropic, OpenAI, or any OpenAI-compatible server) in an agent harness: give it a high-level task in the chat, and it plans the task and carries it out by calling your physical [Skills](/docs/skills) as tools, while a fast monitor model watches each one through the cameras.
- **Recording and training.** First-class CLI commands ([`record`](/docs/commands#recording-commands), ([`train`](/docs/commands#training-and-data-commands)) let you go from teleoperated demonstrations to a trained policy without leaving the framework.
- **Hydra-driven configuration.** Every command takes its config from a YAML file (`robot.yaml`, `controller.yaml`, `server.yaml`, `commands/record.yaml`, …) composed via [Hydra defaults](/docs/project-configs). Each module's config lives in `conf/modules/<module_name>.yaml` matching the attribute name on your `Robot`. A [skill](/docs/skills) config lives in `conf/skills/<skill_name>.yaml`, a [service](/docs/services) config in `conf/services/<service_name>.yaml`, and a [training](/docs/training) run in `conf/training/<training_name>.yaml`.
