# Project Settings

Every Solarian project has a `settings.py` that tells the framework which `Robot`, `Controller`, and `Server` subclasses belong to this project. It's the smallest possible registry — just three string class paths — but it's what lets the CLI run any of them with the right configuration. {{ className: 'lead' }}

The pattern is borrowed from Django: a single Python module per project, loaded lazily, accessible globally as `solarian.conf.settings`.

## The `settings.py` file

A scaffolded project ships with this content (see [`solarian/templates/settings.py.tmpl`](https://github.com/solarian-dev/solarian/blob/main/solarian/templates/settings.py.tmpl)):

```python
"""
Solarian settings for myrobot project.

Generated by 'solarian create-project'.
"""

ROBOT_CLASS = 'myrobot.robot.MyrobotRobot'
CONTROLLER_CLASS = 'myrobot.controller.MyrobotController'
SERVER_CLASS = 'myrobot.server.MyrobotServer'
```

<Properties>
  <Property name="ROBOT_CLASS" type="str">
    Dotted import path to your <a href="/docs/robots"><code>Robot</code></a> subclass. Used by <code>solarian run-robot</code>.
  </Property>
  <Property name="CONTROLLER_CLASS" type="str">
    Dotted import path to your <a href="/docs/controllers"><code>Controller</code></a> subclass. Used by <code>solarian run-controller</code>, <code>run-policy</code>, <code>record</code>, and <code>replay</code>.
  </Property>
  <Property name="SERVER_CLASS" type="str">
    Dotted import path to your <a href="/docs/servers"><code>RelayServer</code></a> subclass. Used by <code>solarian run-server</code>.
  </Property>
</Properties>

You can add any number of additional constants to `settings.py` and read them through `solarian.conf.settings.YOUR_VALUE` from anywhere in your code.

## Where it lives

The CLI looks for `settings.py` in this order ([`solarian/cli/manage.py`](https://github.com/solarian-dev/solarian/blob/main/solarian/cli/manage.py)):

1. The path passed via `--settings`.
2. `<package_name>/settings.py`, where `<package_name>` is the `name` field in your `pyproject.toml` (with hyphens replaced by underscores).
3. The first Python package in the current directory that contains a `settings.py`.
4. `conf/settings.py` (legacy fallback).

A scaffolded project lands in (2): `myrobot/myrobot/settings.py`.

## Environment variables

Once located, the settings path is exported into the environment so that subprocesses (modules forked off the robot, the AI controller's think process) can re-resolve it without needing the original CLI args:

<Properties>
  <Property name="SOLARIAN_SETTINGS" type="env">
    Absolute path to <code>settings.py</code>. Set automatically by the CLI; you can also set it manually if you embed Solarian in a non-CLI script.
  </Property>
  <Property name="SOLARIAN_PROJECT_PATH" type="env">
    Absolute path to your project root. Solarian also <code>sys.path.insert(0, ...)</code>s it so your project package is importable.
  </Property>
  <Property name="SOLARIAN_CONF_PATH" type="env">
    Absolute path to the Hydra config directory (defaults to <code>./conf</code>). Used by every module to find its <code>conf/&lt;module_name&gt;.yaml</code>.
  </Property>
  <Property name="SOLARIAN_CURRENT_CONFIG" type="env">
    Set during command execution to the absolute path of the active config file. Used to print friendlier validation errors.
  </Property>
</Properties>

## Reading settings from your code

Import the lazy singleton:

```python
from solarian.conf import settings

print(settings.ROBOT_CLASS)
```

The first attribute access loads the module from `SOLARIAN_SETTINGS` and caches it. If the environment variable isn't set, you'll get:

```text
ValueError: SOLARIAN_SETTINGS environment variable not set
```

This is the standard error you'll see when you run a script that depends on `solarian.conf.settings` without going through the CLI. Either run via `solarian <subcommand>` or set `SOLARIAN_SETTINGS` yourself before importing.

## Running with custom settings

Two common scenarios:

### Different settings per environment

Keep `settings.py`, `settings_dev.py`, and `settings_prod.py` side by side; pick one explicitly:

```bash
solarian run-robot --settings myrobot/settings_prod.py
```

### Embedding Solarian outside the CLI

When using Solarian from a notebook or your own script:

```python
import os
os.environ["SOLARIAN_SETTINGS"] = "/absolute/path/to/myrobot/settings.py"
os.environ["SOLARIAN_PROJECT_PATH"] = "/absolute/path/to/myrobot"
os.environ["SOLARIAN_CONF_PATH"] = "/absolute/path/to/myrobot/conf"

from solarian.conf import settings
from solarian.utils import get_class

RobotCls = get_class(settings.ROBOT_CLASS)
```

## How the CLI uses settings

When you run a `solarian` subcommand:

1. Resolve `settings.py` (CLI arg or auto-discovery).
2. Set `SOLARIAN_SETTINGS`, `SOLARIAN_PROJECT_PATH`, and `SOLARIAN_CONF_PATH`.
3. Initialize Hydra against the config directory.
4. Compose the YAML for this command (`config_name` from the `CommandRegistry` entry).
5. Call `solarian.setup.setup(modules=...)` to import the project files needed by this command (`robot.py`, `observation.py`, `action.py`, `controller.py`, `server.py`).
6. Hand the validated config to the command's `handle()`.

This is what makes commands like `run-robot` work without any explicit imports on the user side: the CLI imports your project's `robot.py`, which imports your `Robot` subclass, which references your modules — and the settings module is the bootstrap point for that whole chain.
