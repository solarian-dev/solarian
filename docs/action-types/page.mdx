# Action Types

Every [Action](/docs/actions) carries an integer `action_type` that tells the robot how to dispatch it. Standard types like `MODULE_ACTION` flow into a module's action queue; custom types are dispatched to robot- or module-level methods registered with `@action_handler`. {{ className: 'lead' }}

Defined in [`solarian/core/action.py`](https://github.com/solarian-dev/solarian/blob/main/solarian/core/action.py).

## The `ActionType` class

`ActionType` is a lightweight integer-style class (not a true `IntEnum` — it supports subclass extension without enum-validation conflicts):

```python
class ActionType:
    STOP             = 0
    MODULE_ACTION    = 1
    SCHEDULE_WAYPOINT = 2
    RESTART_PUT      = 3
    START_SKILL      = 4
    STOP_SKILL       = 5
    CUSTOM_START     = 100
```

<Properties>
  <Property name="STOP" type="int = 0">
    Tells a module to stop its run loop. The default <code>_dispatch_action</code> handles it by returning <code>False</code>.
  </Property>
  <Property name="MODULE_ACTION" type="int = 1">
    The most common type. The action carries one or more <code>ModuleAction</code> sub-actions in <code>action.data</code>; the robot pushes each one onto the corresponding module's <code>action_queue</code>.
  </Property>
  <Property name="SCHEDULE_WAYPOINT" type="int = 2">
    Tells a module to move a target value. Core <code>Module</code> implements this with a <code>TrajectoryInterpolator</code> (pose or scalar) selected by yaml <code>{'interpolator_type'}</code>. Covers both streaming and exclusive go-to moves — see <a href="#waypoint-params">Waypoint params</a> and <a href="/docs/modules/scheduling-waypoints">Scheduling Waypoints</a>.
  </Property>
  <Property name="RESTART_PUT" type="int = 3">
    Resets a module's internal <code>put</code> timing — used when the controller resynchronizes the rate.
  </Property>
  <Property name="START_SKILL" type="int = 4">
    Start a registered skill by name, carrying <code>{'{"skill": name, "params": {...}}'}</code>. Module names the skill writes live in <code>params["arm"]</code> / <code>params["gripper"]</code>. One shape for two channels: on the <code>skill_command_queue</code> it asks the controller to start the skill, and on the wire to the robot it asks the robot to. The direction is the channel's, not the type's. Never forwarded to a module.
  </Property>
  <Property name="STOP_SKILL" type="int = 5">
    The counterpart to <code>START_SKILL</code>, carrying just the name.
  </Property>
  <Property name="CUSTOM_START" type="int = 100">
    The first integer reserved for user-defined action types. Anything <code>&gt;= 100</code> is yours.
  </Property>
</Properties>

## Waypoint params {{ id: 'waypoint-params' }}

`SCHEDULE_WAYPOINT` covers both streaming teleop and one-shot go-to moves. Which one you get depends on **who supplies the timing**, expressed through the optional `params` dict on a `ModuleAction`:

<Properties>
  <Property name="speed" type="float | None">
    A velocity limit rather than a deadline: <code>moveJ</code> in rad/s, <code>moveL</code> in m/s, gripper in interpolator units/s. <code>None</code> means "use the module default". Merely including the key hands timing to the module.
  </Property>
  <Property name="rot_speed" type="float">
    Rotational limit for <code>moveL</code>, in rad/s.
  </Property>
  <Property name="frame" type="str = 'world'">
    <code>{'"ee"'}</code> composes the Cartesian payload as a delta in the current end-effector frame before moving.
  </Property>
</Properties>

With `speed` present the module drives the target to completion at its speed limit (`moveJ` / `moveL`), taking as long as the distance requires. Without it the caller owns the timing: `drop_timestamps` servos over the module's adaptive drive horizon, and a plain waypoint blends into the trajectory at its own `timestamp`.

A [skill](/docs/skills) builds this envelope itself, keyed by module **name**. Modules interpret actions; they do not manufacture them for someone else, which is what lets the same skill run on the controller or on the robot — a name crosses a link, a `Module` object cannot.

```python
# Streaming: the caller's timestamps drive the trajectory.
Action(
    action_type=ActionType.MODULE_ACTION,
    data={
        "right_arm": {
            "action_type": ActionType.SCHEDULE_WAYPOINT,
            "data": pose_fields,
            "drop_timestamps": True,
        },
        # One action can address several modules; the host splits it per module.
        "right_gripper": {
            "action_type": ActionType.SCHEDULE_WAYPOINT,
            "data": grip_fields,
            "drop_timestamps": True,
        },
    },
)

# Exclusive: including `speed` hands timing to the module.
Action(
    action_type=ActionType.MODULE_ACTION,
    data={
        "right_arm": {
            "action_type": ActionType.SCHEDULE_WAYPOINT,
            "data": joint_fields,
            "params": {"frame": "world", "speed": None},
        }
    },
)
```

## Declaring custom action types

To add your own action types, subclass `ActionType` and define class attributes whose values are `>= ActionType.CUSTOM_START`:

```python
from solarian.core.action import ActionType

class MyActionType(ActionType):
    OPEN_GRIPPER  = ActionType.CUSTOM_START + 0
    CLOSE_GRIPPER = ActionType.CUSTOM_START + 1
    HOMING        = ActionType.CUSTOM_START + 2
```

Solarian's `ActionType.__init_subclass__` validates each value at import time:

- Any value below `CUSTOM_START` that conflicts with a built-in raises `ValueError(f"{name}={val} conflicts with reserved range")`.
- Each new value is registered in `ActionType._registry` so `ActionType.name_of(value)` returns a friendly label.

You can declare as many subclasses as you like across plugins; each adds its own entries to the shared registry.

## Registering handlers

Use the `@action_handler` decorator to bind a method to an action type. The decorated method must return `bool` — `True` to keep the loop running, `False` to stop the module/robot.

### On a `Module`

```python
from solarian.core.module import Module
from solarian.core.action import action_handler, ModuleAction

class GripperModule(Module):
    @action_handler(MyActionType.OPEN_GRIPPER)
    def _on_open(self, action: ModuleAction, t_now: float) -> bool:
        self.write_actuators({"pos": 1.0})
        return True

    @action_handler(MyActionType.CLOSE_GRIPPER)
    def _on_close(self, action: ModuleAction, t_now: float) -> bool:
        self.write_actuators({"pos": 0.0})
        return True
```

The module's run loop drains its `action_queue` each tick, looks up the handler in `self.action_handlers`, and dispatches.

### On a `Robot`

```python
from solarian.core import Robot
from solarian.core.action import action_handler

class MyRobot(Robot):
    arm = ArmModule()
    gripper = GripperModule()

    @action_handler(MyActionType.HOMING)
    def _on_homing(self, action, t_now) -> bool:
        for module in self.modules.values():
            module.action_queue.put(MoveToHomeAction(...))
        return True
```

The robot's control loop dispatches non-`MODULE_ACTION` actions through `Robot.action_handlers`. Useful for fan-out commands (one incoming action that affects multiple modules).

## Sending a custom action from a controller

Set `action.action_type` and put your payload in `action.data`. Custom action types use the raw `data` dict — `Action.zeros()` and the per-module path don't apply:

```python
from solarian.core.action import Action

class MyController(Controller):
    def control_step(self) -> Action:
        if self.want_to_open_gripper:
            self.want_to_open_gripper = False
            action = Action()
            action.action_type = MyActionType.OPEN_GRIPPER
            action.data = {"target_force": 0.5}
            return action
        # otherwise return a normal MODULE_ACTION
        ...
```

The robot will look up the handler with the matching `action_type`, ignoring whether it lives on the `Robot` itself or on one of its `Module`s. Module-level handlers fire for actions placed on that module's queue; robot-level handlers fire for actions whose type isn't `MODULE_ACTION`.

## Naming conventions

- **Use a subclass per logical group of actions.** One per plugin or per high-level capability (`GripperActionType`, `NavigationActionType`, …) keeps namespaces clean.
- **Always offset from `CUSTOM_START`.** The reserved range catches collisions early.
- **Keep handler return values explicit.** A `True` keeps the loop alive; a `False` is interpreted as "stop this module" (or "stop this robot" at the robot level). Don't let a handler accidentally fall through to `None`.
