# Creating a Project

This guide walks through creating a brand-new Solarian project and running the three nodes — relay server, robot, and controller — for the first time. The scaffold includes a local arm. By the end you'll have a keyboard teleop session that nudges that arm. {{ className: 'lead' }}

## 1. Scaffold a project

`create-solarian` is shipped as a separate entry point so it works before you have a project on disk.

```bash
create-solarian my_robot
cd my_robot
```

The name is the directory, the Python package, and the class prefix. `my_robot` imports as `my_robot`. Title-casing it gives `MyRobot`, so the generated classes are `MyRobotRobot`, `MyRobotController`, and `MyRobotServer`.

The scaffolder produces a project with this layout:

<ScaffoldFigure name="my_robot" />

`conf/` is organized by who reads each file; [Project Configs](/docs/project-configs#the-conf-folder) covers every folder. Skills you write go in a `skills/` package next to `modules/`, and custom [action types](/docs/actions#custom-action-types) in `action.py` beside the schema that uses them.

The generated [`my_robot/settings.py`](/docs/settings) wires the project together by class path:

```python
ROBOT_CLASS = 'my_robot.robot.MyRobotRobot'
CONTROLLER_CLASS = 'my_robot.controller.MyRobotController'
SERVER_CLASS = 'my_robot.server.MyRobotServer'
```

Install the project so the package is importable. `.[all]` is every node on one machine. Use `.[robot]`, `.[server]`, or `.[controller]` when the nodes run on separate machines:

```bash
pip install -e ".[all]"
```

## 2. The arm module

The scaffold writes a local arm and attaches it. `my_robot/robot.py`:

```python
from solarian.core import Robot

# Import module classes from your local modules or third party module plugins
from my_robot.modules.my_arm_module import MyArmModule

# Define your robot here
class MyRobotRobot(Robot):
    # Define robot modules, eg:
    arm = MyArmModule()
```

The attribute name `arm` matches `conf/modules/arm.yaml`. That is how Solarian routes per-module configuration. The generated file sets the module's control rate:

```yaml
frequency: 30
```

`my_robot/modules/my_arm_module.py` subclasses [`ArmModule`](/docs/modules) with the actuator commented out, so the project runs before any servo driver is installed:

```python
from solarian.core.arm_module import ArmModule
#from solarian_feetech.actuator import FeetechServo
from solarian.core.action import ActionType, ModuleAction, action_handler


class MyArmModule(ArmModule):
    # declare actuators and sensors
    #shoulder_pan = FeetechServo()
    pass
```

To drive a Feetech servo, install the driver and uncomment those two lines:

```bash
solarian install feetech
```

```python
from solarian.core.arm_module import ArmModule
from solarian_feetech.actuator import FeetechServo
from solarian.core.action import ActionType, ModuleAction, action_handler


class MyArmModule(ArmModule):
    # declare actuators and sensors
    shoulder_pan = FeetechServo()
```

A ready-made module is the other path. [`solarian install`](/docs/plugins#installing-a-plugin) installs the plugin and copies its YAML into `conf/modules/`. The attribute name on the robot has to match that filename. See [Core Plugins](/docs/plugins#core-plugins).

## 3. Define an observation and an action schema

Solarian uses Pydantic-typed [`Observation`](/docs/observations) and [`Action`](/docs/actions) classes to describe what flows over the wire. The scaffolder generates a schema whose `arm` attribute matches the robot, with the joint field commented out until the module declares it:

```python
from solarian.core.observation import SensorField, ModuleObs, Observation
from my_robot.robot import MyRobotRobot


class MyArmObs(ModuleObs):
    # define fields here
    # shoulder_pan_pos = SensorField(MyRobotRobot.arm.shoulder_pan.pos)
    pass


class MyRobotObservation(Observation):
    arm = MyArmObs()
```

```python
from solarian.core.action import ModuleAction, Action, ActuatorField
from my_robot.robot import MyRobotRobot

# Example arm module action
class MyArmAction(ModuleAction):
    #shoulder_pan = ActuatorField(MyRobotRobot.arm.shoulder_pan.pos)
    pass


# Define your Action class here
class MyRobotAction(Action):
    arm = MyArmAction()
```

Once `MyArmModule` declares `shoulder_pan`, uncomment the field and drop `pass`:

```python
class MyArmObs(ModuleObs):
    shoulder_pan_pos = SensorField(MyRobotRobot.arm.shoulder_pan.pos)


class MyRobotObservation(Observation):
    arm = MyArmObs()
```

```python
class MyArmAction(ModuleAction):
    shoulder_pan = ActuatorField(MyRobotRobot.arm.shoulder_pan.pos)


class MyRobotAction(Action):
    arm = MyArmAction()
```

## 4. Wire up keyboard teleop in the controller

The generated `my_robot/controller.py` is an empty `MyRobotController`. Every controller comes with a keyboard module that turns key transitions into [events](/docs/events). Handle them with `@event_handler`, and return an action from `control_step`:

```python
from solarian.core import Controller
from solarian.core.action import ActionType
from solarian.core.event import Event, EventType, event_handler
from my_robot.action import MyRobotAction

class MyRobotController(Controller):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self.target = MyRobotAction.zeros()

    @event_handler(EventType.KEY_DOWN)
    def on_key_down(self, event: Event):
        if event.data["key"] == 'a':
            self.target.arm.shoulder_pan.value -= 0.05
        elif event.data["key"] == 'd':
            self.target.arm.shoulder_pan.value += 0.05

    def control_step(self) -> MyRobotAction:
        self.target.action_type = ActionType.MODULE_ACTION
        return self.target
```

Handlers run on the control thread when the tick drains, so they never race the control loop. For keys you *hold* rather than tap, read `self.held_keys` in `control_step` instead.

See [Controllers](/docs/controllers) for the full lifecycle, [Events](/docs/events) for other input devices, and [Action types](/docs/actions#action-types) for the enum.

## 5. Run the three nodes

For local development you can run all three nodes on the same machine using the default `conf/deployment/localhost.yaml`:

<CodeGroup>

```bash {{ title: 'Terminal 1: relay server' }}
solarian run-server
```

```bash {{ title: 'Terminal 2: robot' }}
solarian run-robot
```

```bash {{ title: 'Terminal 3: controller' }}
solarian run-controller
```

</CodeGroup>

To split nodes across machines, add `conf/deployment/lab.yaml` with the relay's IP and each machine's device paths, then launch every node with `--deployment lab`. See [Deployments](/docs/project-configs#deployments).

## 6. Confirm everything works

In the controller window, press `a` and `d` to nudge `shoulder_pan`. You should see the corresponding actuator move. The relay server window logs every action and observation it forwards.

<Note>
  If something doesn't move, double-check that the module attribute name (`arm`) matches the YAML filename (`conf/modules/arm.yaml`) **and** the `Observation`/`Action` attribute names. Solarian validates these at class definition time and will raise a `TypeError` if they disagree.
</Note>

## Where to go next

- **Calibrate the hardware** with `solarian calibrate` before first `run-robot` on a real arm or gripper — see [Calibration](/docs/modules/calibration).
- **Add more modules** with `solarian install <plugin>` — see [Core Plugins](/docs/plugins#core-plugins).
- **Record a dataset** of teleoperated demonstrations: `solarian record`.
- **Curate it** with a dataset op: `solarian add-op <name>` writes one into `datasets/` — see [Dataset ops](/docs/datasets#dataset-ops).
- **Replace the controller** with a learned policy, served with `solarian run-service <skill conf>` and driven by a skill, or with the [AI Controller](/docs/ai_controller) for VLM-driven control.
- **Train a policy** with `solarian train --conf conf/training/<run>`.
