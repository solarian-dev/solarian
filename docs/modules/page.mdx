# Modules

A **Module** is anything connected to the runtime — an arm, a gripper, a camera, a base, a leg, a keyboard, a joystick. It bundles together every actuator and sensor on the same hardware port and ticks at its own configurable rate. {{ className: 'lead' }}

Each module is responsible for:

- Reading its sensors and writing its actuators on a real-time loop.
- Publishing observations into a shared-memory ring buffer the [`Robot`](/docs/robots) drains at `cfg.fps`.
- Emitting [events](/docs/events) for the discrete things that happen to it.
- Pulling actions off a shared-memory queue and dispatching them to `@action_handler`-decorated methods.
- Optional one-time setup (`initialize`), and per-tick logic (`control_step`).

Defined in [`solarian/core/module.py`](https://github.com/solarian-dev/solarian/blob/main/solarian/core/module.py). `Module` is an abstract class; *how* it is scheduled is a separate property — see [Execution Modes](#execution-modes).

## Declaring a Module

Subclass `Module` and attach `Actuator` / `Sensor` instances as **class attributes**. Each attribute name becomes the canonical identifier for that hardware component.

```python
from solarian.core.module import Module
from solarian_feetech.actuator import FeetechServo

class ArmModule(Module):
    shoulder_pan = FeetechServo(model="sts3215")
    shoulder_lift = FeetechServo(model="sts3215")
    elbow_flex = FeetechServo(model="sts3215")
    wrist_flex = FeetechServo(model="sts3215")
    wrist_roll = FeetechServo(model="sts3215", is_continuous=True)
    gripper = FeetechServo(model="sts3215")
```

Then attach the module to your `Robot`:

```python
from solarian.core import Robot

class MyRobot(Robot):
    arm = ArmModule()
```

The attribute name on the robot (`arm`) is used to load `conf/arm.yaml` and to key your `Observation` and `Action` schemas.

<Note>
  An <code>Actuator</code> that also implements the <code>Sensor</code> interface (a <code>Servo</code>) is registered on both sides — you can read its position back as part of your <code>Observation</code> and command its position as part of your <code>Action</code>.
</Note>

## Module configuration

Each module gets its own YAML config under `conf/<module_attribute_name>.yaml`. The fields map to [`ModuleConfig`](https://github.com/solarian-dev/solarian/blob/main/solarian/core/configs.py):

```yaml
# conf/arm.yaml
actuator_port: /dev/ttyUSB0
frequency: 200
actuators:
  shoulder_pan:
    id: 1
    port: ${actuator_port}
    sim_joint: "arm/shoulder_pan"
    sim_range_min: -1.92
    sim_range_max: 1.92
  shoulder_lift:
    id: 2
    port: ${actuator_port}
  # ...
```

<Properties>
  <Property name="frequency" type="float">
    Module control loop rate in Hz. Each module ticks independently at this rate.
  </Property>
  <Property name="get_max_k" type="int">
    Max number of observation samples kept in the shared-memory ring buffer (default 128).
  </Property>
  <Property name="commands_per_cycle" type="int">
    Max number of actions drained per control loop iteration.
  </Property>
  <Property name="command_queue_size" type="int">
    Capacity of the shared-memory action queue.
  </Property>
  <Property name="actuators" type="dict[str, ActuatorConfig]">
    Per-actuator configuration keyed by the class attribute name.
  </Property>
  <Property name="sensors" type="dict[str, SensorConfig]">
    Per-sensor configuration keyed by the class attribute name.
  </Property>
  <Property name="actuators.*.real_range_*" type="int | None">
    Measured Present-frame ends of travel, written by <code>solarian calibrate</code>. See <a href="/docs/modules/calibration">Calibration</a>.
  </Property>
  <Property name="actuators.*.center_offset" type="int | None">
    Encoder-zero shift so Present travel is a linear window. Legacy yaml <code>homing_offset</code> is still read. See <a href="/docs/modules/calibration">Calibration</a>.
  </Property>
  <Property name="interpolator_type" type="InterpolatorType">
    One of <code>joint</code>, <code>scalar</code>, or <code>pose</code>. Selects the trajectory interpolator used by the default <code>SCHEDULE_L / SCHEDULE_J</code> handler. See <a href="/docs/modules/scheduling-waypoints">Scheduling Waypoints</a>.
  </Property>
  <Property name="execution" type="ExecutionMode | None">
    Overrides the class's <code>execution_mode</code> for this deployment. See <a href="#execution-modes">Execution Modes</a>.
  </Property>
</Properties>

To add module-specific config fields, set `config_class` on your subclass:

```python
from solarian.core.configs import ModuleConfig

class ArmConfig(ModuleConfig):
    home_position: list[float] = [0.0] * 6
    max_torque: float = 1.0

class ArmModule(Module):
    config_class = ArmConfig
    shoulder_pan = FeetechServo()
    # ...
```

Solarian validates `conf/arm.yaml` against `ArmConfig` and exposes it as `self.cfg.home_position`, `self.cfg.max_torque`, etc.

## The `initialize` method

`initialize()` runs **once** in the parent process, after `connect()` and before `start()`. Use it for hardware setup that should happen exactly once (setting torque, choosing an operating mode, homing).

```python
class ArmModule(Module):
    shoulder_pan: FeetechServo = FeetechServo()
    # ...

    def initialize(self):
        super().initialize()
        self.disable_torque()
        self.configure_components({"Operating_Mode": 0})  # position mode
        self.enable_torque()
```

The base implementation is a no-op, so calling `super().initialize()` is optional but encouraged.

## The `control_step` method

`control_step()` is called every iteration of the module's run loop, *after* incoming actions are drained and *before* observations are published. This is where you put fast inner-loop logic — interpolation, feed-forward terms, velocity smoothing, anything that has to happen at the module's `frequency`.

```python
from solarian.core.module import Module
from solarian.core.action import ActionType, ModuleAction, action_handler

class ArmModule(Module):
    shoulder_pan = FeetechServo()
    # ...

    def initialize(self):
        super().initialize()
        self.next_position = None

    def control_step(self):
        if self.next_position is not None:
            self.write_actuators(self.next_position)
            self.next_position = None
```

`control_step` is **abstract**: every module says explicitly what it does per tick, even if the answer is nothing. Modules that only stream sensor data — cameras, for instance — override it with an empty body rather than inheriting a silent no-op.

Actuator modules already implement it. `ActuatorModule.control_step` samples the active trajectory interpolator and writes the result, which is what makes `SCHEDULE_L / SCHEDULE_J` work; `ArmModule` and `GripperModule` inherit that. Override it only if you need something else.

## Action handlers

Actions arrive at a module through its shared-memory `ModuleActionQueue`. The module's run loop drains the queue each tick and dispatches each action to a method registered with `@action_handler`.

```python
from solarian.core.action import action_handler, ActionType, ModuleAction

class ArmModule(Module):
    shoulder_pan = FeetechServo()
    # ...

    @action_handler(ActionType.MOVE_J)
    def _on_schedule_waypoint(self, action: ModuleAction, t_now: float) -> bool:
        self.next_position = [field.value for field in action.values()]
        return True   # return False to stop the module
```

The decorator stores the action type on the method (`method._handles_action`), and `Module.__init__` walks the class to build a `dict[int, str]` mapping action types to method names.

A handler must return a `bool`:

- `True` to keep the module running.
- `False` to stop the module's process cleanly.

If an action arrives with no registered handler, the module logs a warning and ignores it.

See [Action Types](/docs/action-types) for the standard types (`STOP`, `MODULE_ACTION`, `SCHEDULE_L / SCHEDULE_J`, `RESTART_PUT`) and how to declare your own. For the built-in pose/scalar waypoint path — streaming and exclusive speed-limited moves alike — see [Scheduling Waypoints](/docs/modules/scheduling-waypoints).

## Who builds the actions

A module interprets actions; it does not build them for anyone else. That asymmetry is deliberate: the caller is usually a [skill](/docs/skills), which addresses modules by **name** so the same skill can run on the controller or on the robot. A name crosses a link, a `Module` object cannot, so giving modules builder methods would have quietly tied every skill to running in the same process as its hardware.

A skill therefore constructs the [`SCHEDULE_L / SCHEDULE_J` envelope](/docs/action-types#waypoint-params) itself, and one `Action` may key several modules at once.

### Named poses

A pose name like `"home"` is the *skill's* vocabulary, not a module's — the module knows its ends of travel and its speed limits, which are facts about the hardware, but nothing about what a task considers home. So named poses live in the skill's `conf/<config_name>.yaml`, keyed pose then module then actuator, in each actuator's own command units (normalized `[-100, 100]` for a range-mode servo, mm of aperture for a gripper):

```yaml
# conf/move.yaml
poses:
    home:
        right_arm:
            shoulder_pan: 0.0
            shoulder_lift: -80.4
            elbow_flex: 69.5
            wrist_flex: -46.0
            wrist_yaw: 0.0
            wrist_roll: 0.0
        right_gripper:
            gripper: 85.0
```

`MoveSkill(params={"pose": "home", "arm": "right_arm", "gripper": "right_gripper"})` looks up that pose and sends each module its own targets. A dict in `pose` is an inline joint or Cartesian target for the arm instead.

## Execution modes

*What* a module is and *how* it is scheduled are separate concerns. A camera is conceptually a `CameraModule`; "runs in its own process" is an operational decision about it. Keeping the two apart means you can change one without touching the other — and it keeps the class hierarchy from encoding your deployment topology.

So a module declares a default and the runtime builds the matching **runner**:

<Properties>
  <Property name="ExecutionMode.PROCESS" type="process">
    Its own OS process. For cameras, arms, grippers — expensive or high-frequency hardware whose timing must not be disturbed by anything else. The default.
  </Property>
  <Property name="ExecutionMode.THREAD" type="thread">
    A daemon thread on the host. For blocking device APIs: joystick/HID readers, serial event sources.
  </Property>
  <Property name="ExecutionMode.INLINE" type="inline">
    Ticked by the host's own control loop. For cheap, event-driven modules like a keyboard, where a dedicated process would buy isolation nobody needs and add a queue hop to every keypress.
  </Property>
</Properties>

```python
class CameraModule(Module):
    execution_mode = ExecutionMode.PROCESS

class KeyboardModule(Module):
    execution_mode = ExecutionMode.INLINE
```

All three expose the same external interface — `start()`, `stop()`, `is_alive()`, `join()` — so nothing that uses a module has to know which it got. The class attribute is only a default: override it per instance, or per deployment in YAML.

```python
camera = CameraModule(execution_mode=ExecutionMode.INLINE)   # e.g. in a test
```

```yaml
# conf/camera.yaml
execution: process
```

The same axis applies to [skills](/docs/skills#where-the-skill-runs-executionplace-and-executionmode), which share the runner machinery.

## The run loop

`module.start()` hands the module to its runner, which drives the same three-step worker protocol whatever the execution mode:

```text
worker_setup(reconnect)
   │   reconnect hardware when forked — the parent's handles do not survive fork
   └── reset()

worker_tick()                       ← looped by the runner, or called by the
   ├── drain action_queue  →  _dispatch_action(action, t_now)     host's own
   ├── control_step()                                             tick when INLINE
   └── update_observations()   (writes to shared-memory ring buffer)

worker_teardown(exit_reason)
```

`PROCESS` and `THREAD` runners own the loop and its `precise_wait(1/frequency)` regulation; the `INLINE` runner sets up once and ticks on the host's loop instead.

The first successful iteration marks the module ready, telling the parent `Robot` that it is live and the next observation is real.

## Sensor reads and observation publishing

`update_observations()` walks every sensor on the module, reads its current value (through the `ComponentBus` if needed), wraps it in the appropriate [`Data`](/docs/core) subclass, and writes a snapshot into the module's `ObservationBuffer`. The robot's `_observation_sender` thread reads the latest snapshot from each module and combines them into a single [`Observation`](/docs/observations) at the configured `fps`.

You don't normally call `update_observations()` yourself — it's called for you at the end of every iteration.

It is the one way a module reports state, whichever runner hosts it. A module in its own process publishes across shared memory; a module inline on a controller's loop publishes into a local `ObservationBuffer.local()`, which accepts any Python object rather than only numbers and arrays. Either way a [skill](/docs/skills) reads it the same way, so a leader arm on the controller offers its joint positions to a teleop skill exactly as a follower arm on the robot does.

A module whose state has no entry in the project's `Observation` schema — a leader arm, a keyboard — has nothing typed to publish, so it overrides `update_observations()` and puts what it does have:

```python
class KeyboardModule(Module):
    def update_observations(self):
        self.observation_buffer.put({"held_keys": self.held_keys})
```

## Emitting events

Observations say what the world looks like; **events** say what just happened. A module declares the types it produces and calls `emit()`:

```python
from solarian.core.event import EventType

class FootPedalModule(Module):
    events = (EventType.BUTTON_DOWN, EventType.BUTTON_UP)

    def control_step(self):
        if self._pedal_just_went_down():
            self.emit(EventType.BUTTON_DOWN, button="pedal")
```

`emit()` writes to a sink the runner provides — a `deque` for inline and threaded modules, a `multiprocessing.Queue` for process-backed ones — and the host reads them back with `drain_events()` on its own control tick. Keep the payload small and picklable.

Reserve events for transitions. Continuous signals stay observations, so that the event path remains useful for the discrete things it is good at. See [Events](/docs/events).

## Multi-port modules

If your module has actuators on more than one port (for example, two daisy-chained Dynamixel buses), Solarian groups them by `actuators[name].port` into `self.actuators_by_port` and creates one `ModuleBus` per port. If two **different modules** share a port, the parent `Robot` automatically starts a `BusServer` and gives each module a `BusClient` proxy — no work on your end.
