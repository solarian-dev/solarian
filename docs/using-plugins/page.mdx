# Using Plugins

Plugins are ordinary `pip` packages, so the baseline is always `pip install solarian-<name>`. But most plugins need a config file and a reference in your code, so Solarian ships helpers that wire everything up for you. This page covers installing and using each kind of plugin. {{ className: 'lead' }}

## Install a plugin

[`solarian install`](/docs/commands#install) does three things:

```bash
solarian install feetech
```

1. **Installs the package** into the current Python environment. A short name is prefixed, so `feetech` installs `solarian-feetech`. PyPI is tried first; if the project is not published, the command looks for `solarian-feetech/` in the current folder and then under `plugins/`.
2. **Copies the default config** into `conf/` when the destination is absent. A file in the package's `templates/` directory keeps its folder and name (`templates/skills/move.yaml` → `conf/skills/move.yaml`, `templates/modules/feetech.yaml` → `conf/modules/feetech.yaml`).
3. **Records the dependency** — adds `solarian-feetech>=0.1.0` to the project's `pyproject.toml`.

The Robot attribute has to match that filename. A second instance (a left arm and a right arm from one plugin) is a copy of the yaml under the new name.

### Attach it to your Robot

`solarian install` never edits your Python — you import the class and attach it yourself:

```python
from solarian.core import Robot
from solarian_ur5.module import UR5ArmModule

class MyRobot(Robot):
    ur5 = UR5ArmModule()   # reads conf/modules/ur5.yaml
```

Then edit `conf/modules/ur5.yaml` to set ports, servo IDs, frequency, and calibration paths for your hardware. See [Project Configs](/docs/project-configs).

### A local path

Pass a path to skip PyPI and install that directory editable:

```bash
solarian install plugins/solarian-umi-slim
```

## Skill plugins

[Skill](/docs/skills) plugins use the same install. Any package that advertises a `solarian.skills` entry point is **auto-discovered** by every [`AIController`](/docs/ai_controller) — Solarian reads the entry points via `importlib.metadata` at startup and merges them into `available_skills`. You can also import the class and start it yourself:

```python
from solarian_move_skill import MoveSkill
from solarian_umi_skill import UMISkill

MoveSkill(params={"pose": "home", "arm": "right_arm", "gripper": "right_gripper"})
UMISkill(params={"config": "cup_arrange.yaml"})
```

`pose` is any name under `poses:` in `conf/skills/move.yaml`, which `solarian install solarian-move-skill` creates from the plugin's template when the file is not already there. `config` is a yaml in `conf/`. `solarian install solarian-umi-skill` copies `templates/umi.yaml` to `conf/skills/umi.yaml`; copy that file for each policy.

Class-attribute skills you declare on your controller take priority over a discovered skill of the same name, so you can still override one by declaring it explicitly.

`UMISkill` reads the checkpoint and the rest of its parameters from the file you passed. `arm`, `gripper`, and `camera` live in that file too:

```yaml
# conf/skills/cup_arrange.yaml — one UMI policy
policy_server_url: http://localhost:8001
policy_server:
  managed: false
  checkpoint: data/models/cup_wild_vit_l_1img.ckpt
arm: right_arm
gripper: right_gripper
camera: right_wrist_camera
```

## Policy plugins: train & serve

[Policy](/docs/policies) plugins ship the trainer and the server a skill calls over HTTP. Install the plugin (with the extra you need), then use the CLI:

```bash
pip install "solarian-policy-diffusion[serve]"   # torch, etc. for inference
# or [train] to train, [modal] for cloud training with solarian modal-train

# serve the checkpoint a skill drives (resolves the skill's config)
solarian run-policy umi --config cup_arrange.yaml

# or launch the server directly
solarian-diffusion-policy --input <checkpoint.ckpt> --port 8001
```

Trainers register under `solarian.trainers`, so `solarian train` can select them by name (`model.type=diffusion`). See [Training](/docs/training).

## Command plugins

A plugin can add its own `solarian` subcommand via the `solarian.commands` entry-point group. Once the package is installed, the command shows up in `solarian --help`:

```bash
# shipped by solarian-feetech
solarian feetech-set-id
```

## Mixing plugins in one module

Because each `Actuator` binds its own `bus_class`, a single [Module](/docs/modules) can mix drivers from different plugins. Actuators that share a port share a bus instance; the rest each get their own:

```python
from solarian.core.module import Module
from solarian_feetech.actuator import FeetechServo
from solarian_dynamixel.actuator import DynamixelServo

class MixedArmModule(Module):
    shoulder = FeetechServo(id=1, model="sts3215")
    elbow = FeetechServo(id=2, model="sts3215")
    gripper = DynamixelServo(id=1, model="xl330-m077")
```

## Verifying what's installed

Plugins are regular distributions, so normal tooling works:

```bash
pip show solarian-feetech          # metadata + version
pip list | grep solarian-          # every installed Solarian plugin
```
