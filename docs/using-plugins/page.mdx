# Using Plugins

Plugins are ordinary `pip` packages, so the baseline is always `pip install solarian-<name>`. But most plugins need a config file and a reference in your code, so Solarian ships helpers that wire everything up for you. This page covers installing and using each kind of plugin. {{ className: 'lead' }}

## Hardware modules: `add-module`

The fastest path to using a hardware plugin is [`solarian add-module`](/docs/commands#add-module). One command does three things:

```bash
solarian add-module feetech gripper
```

1. **Installs the package** — `pip install solarian-feetech` (skipped if already installed).
2. **Copies the default config** — the plugin's bundled `conf.yaml` → `conf/gripper.yaml` in your project.
3. **Records the dependency** — adds `solarian-feetech>=0.1.0` to your project's `pyproject.toml`.

The first argument (`feetech`) is the plugin's short name; the second (`gripper`) is the **attribute name** you'll use on your `Robot`. They're independent — install one plugin and attach it under several names (e.g. `left_arm` and `right_arm` for a bimanual robot):

```bash
solarian add-module ur5 left_arm
solarian add-module ur5 right_arm   # same plugin, second config
```

### Attach it to your Robot

`add-module` never edits your Python — you import the class and attach it yourself. The install output prints the exact import path:

```python
from solarian.core import Robot
from solarian_ur5.module import UR5ArmModule

class MyRobot(Robot):
    arm = UR5ArmModule()
```

Then edit `conf/arm.yaml` to set ports, servo IDs, frequency, and calibration paths for your hardware. See [Project Configs](/docs/project-configs).

### Local / editable installs

During development (or to use an unpublished plugin), pass a **path** instead of a name. `add-module` detects the path, installs it editable (`pip install -e`), and finds the bundled `conf.yaml` in the source tree:

```bash
solarian add-module ./plugins/solarian-umi-slim gripper
```

This is exactly how the in-repo reference plugins are consumed from the monorepo.

## Skill plugins: install and go

[Skill](/docs/skills) plugins need no wiring at all. Any package that advertises a `solarian.skills` entry point is **auto-discovered** by every [`AIController`](/docs/ai_controller) — Solarian reads the entry points via `importlib.metadata` at startup and merges them into `available_skills`:

```bash
pip install solarian-skill-cup-arrange
```

The skill's entry-point name (e.g. `cup_arrange`) becomes the name the planner VLM uses. Class-attribute skills you declare on your controller take priority, so you can still override or re-configure a discovered skill by declaring it explicitly.

Point a skill at its checkpoint and policy server through your project's `conf/<skill>.yaml` (the config name is a class attribute on the skill):

```yaml
# conf/cup_arrange.yaml — overrides the plugin's bundled defaults
policy_server_url: http://localhost:8001
policy_server:
  managed: false
  checkpoint: data/models/cup_wild_vit_l_1img.ckpt
```

## Policy plugins: train & serve

[Policy](/docs/policies) plugins ship the trainer and the server a skill calls over HTTP. Install the plugin (with the extra you need), then use the CLI:

```bash
pip install "solarian-policy-diffusion[serve]"   # torch, etc. for inference
# or [train] to train, [modal] for cloud training

# serve the checkpoint a skill drives (resolves the skill's config)
solarian run-policy cup_arrange

# or launch the server directly
solarian-diffusion-policy --input <checkpoint.ckpt> --port 8001
```

Trainers register under `solarian.trainers`, so `solarian train` can select them by name (`model.type=diffusion`). See [Training](/docs/training).

## Command plugins

A plugin can add its own `solarian` subcommand via the `solarian.commands` entry-point group. Once the package is installed, the command shows up in `solarian --help`:

```bash
# shipped by solarian-feetech
solarian feetech-set-id
```

## Mixing plugins in one module

Because each `Actuator` binds its own `bus_class`, a single [Module](/docs/modules) can mix drivers from different plugins. Actuators that share a port share a bus instance; the rest each get their own:

```python
from solarian.core.module import Module
from solarian_feetech.actuator import FeetechServo
from solarian_dynamixel.actuator import DynamixelServo

class MixedArmModule(Module):
    shoulder = FeetechServo(id=1, model="sts3215")
    elbow = FeetechServo(id=2, model="sts3215")
    gripper = DynamixelServo(id=1, model="xl330-m077")
```

## Verifying what's installed

Plugins are regular distributions, so normal tooling works:

```bash
pip show solarian-feetech          # metadata + version
pip list | grep solarian-          # every installed Solarian plugin
```
