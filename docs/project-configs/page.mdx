# Project Configs

Solarian uses [Hydra](https://hydra.cc/) for configuration. All YAML lives under your project's `conf/` directory and is composed by the CLI based on which subcommand you run. The naming and layout follow simple conventions that bind YAML files to Python attributes. {{ className: 'lead' }}

## The `conf/` folder

A scaffolded project's `conf/` looks like this:

```text
conf/
├── robot.yaml              # used by `solarian run-robot`
├── controller.yaml         # used by `solarian run-controller`
├── server.yaml             # used by `solarian run-server`
├── record.yaml             # used by `solarian record`
├── replay.yaml             # used by `solarian replay`
├── train.yaml              # used by `solarian train`
└── deployment/
    └── localhost.yaml      # relay address and device ports for one host layout
```

Every CLI subcommand declares a `config_name` in [`solarian/cli/commands/__init__.py`](https://github.com/solarian-dev/solarian/blob/main/solarian/cli/commands/__init__.py). When you run the command, Hydra loads the matching `conf/<config_name>.yaml`.

| Command | Config file |
|---------|-------------|
| `run-robot` | `conf/robot.yaml` |
| `run-controller` | `conf/controller.yaml` |
| `run-server` | `conf/server.yaml` |
| `record` | `conf/record.yaml` |
| `replay` | `conf/replay.yaml` |
| `train` | `conf/train.yaml` |

## What is a config?

A config is a Hydra-composed YAML document validated by a Pydantic model. Composition lets you split shared values (like ZMQ port numbers) into reusable groups; validation catches typos before the robot starts moving.

For example, `conf/robot.yaml`:

```yaml
connection: ${deployment.connection}

img_compression_quality: 70
fps: 30
```

`${deployment.connection}` pulls the `connection:` block out of the active [deployment](#deployments). After resolution the runtime config looks like:

```yaml
img_compression_quality: 70
fps: 30
connection:
  ip: 127.0.0.1
  action_sender_port: 5555
  action_receiver_port: 5556
  state_sender_port: 5557
  state_receiver_port: 5558
  clock_sync_port: 5559
```

The result is validated against [`RobotConfig`](https://github.com/solarian-dev/solarian/blob/main/solarian/core/configs.py). If a field is missing or has the wrong type, Solarian prints a friendly error and refuses to start.

## Module configs and the naming rule

Each [Module](/docs/modules) attached to your `Robot` reads its own YAML file under `conf/`. **The YAML filename must match the attribute name on your `Robot` subclass.**

```python
class MyRobot(Robot):
    arm = ArmModule()              # → conf/arm.yaml
    gripper = GripperModule()      # → conf/gripper.yaml
    head_camera = CameraModule()   # → conf/head_camera.yaml
```

Each file is parsed against the module's `config_class` (default `ModuleConfig`):

```yaml
# conf/arm.yaml
calibration_file: .cache/calibration/ur5_follower_arm.json
actuator_port: 10.0.0.92
frequency: 120
actuators:
  shoulder_pan:
    id: 0
    model: ur5
    port: ${actuator_port}
    type: ur5_joint
    mode: range_m100_100
  shoulder_lift:
    id: 1
    model: ur5
    port: ${actuator_port}
    type: ur5_joint
    mode: range_m100_100
  # ...
```

This same naming convention drives [Observations](/docs/observations) and [Actions](/docs/actions): `MyObservation.arm` must be a `ModuleObs` whose fields reference `MyRobot.arm.*`.

<Note>
  This is the single most important convention in Solarian. Every consumer of a module — its YAML, its observation, its action, its action queue — finds the module by attribute name. Pick a clear, snake_case name once (e.g. <code>arm</code>, <code>gripper_camera</code>, <code>left_leg</code>) and stick with it.
</Note>

## Variable interpolation

Hydra supports `${var}` interpolation. A common pattern is to declare a shared port at the top of a module config and reuse it for every actuator:

```yaml
actuator_port: /dev/ttyUSB0
actuators:
  joint_1:
    port: ${actuator_port}
  joint_2:
    port: ${actuator_port}
```

Every file in `conf/` can also reference `${deployment.*}`, which is how host-specific values stay in one place. See below.

## Deployments

A **deployment** is everything that changes with *where* your processes run: the relay's address and the device paths as seen from the host that owns the hardware. It lives in `conf/deployment/<name>.yaml`, and the scaffold ships with `localhost.yaml`:

```yaml
connection:
  ip: 127.0.0.1
  action_sender_port: 5555
  action_receiver_port: 5556
  state_sender_port: 5557
  state_receiver_port: 5558
  clock_sync_port: 5559

actuator_port_arm: /dev/ttyUSB0
camera_port_wrist_camera: '0'
```

Every other file in `conf/` reads these through `${deployment.*}`, so moving a robot between machines means editing one file rather than duplicating the directory:

```yaml
# conf/robot.yaml
connection: ${deployment.connection}

# conf/arm.yaml
actuator_port: ${deployment.actuator_port_arm}

# conf/wrist_camera.yaml
camera_port: ${deployment.camera_port_wrist_camera}
```

This works in all three kinds of config file — command, module and skill — even though only command configs go through Hydra composition.

### Selecting a deployment

Add `conf/deployment/pi.yaml` with the Pi's device paths, then pick it per run or once per machine:

```bash
solarian run-robot --deployment pi     # or -d pi
export SOLARIAN_DEPLOYMENT=pi          # e.g. in the Pi's shell profile
```

The default is `localhost`. A name with no matching file is an error listing the available deployments.

<Note>
  A deployment describes the whole topology, not a single machine. If the robot runs on a Pi while you teleop from a laptop, one deployment file holds the Pi's paths for the robot's modules *and* the laptop's paths for the controller's modules. See [Server](/docs/servers) for the full topology.
</Note>

## Hydra `defaults` composition

Hydra's `defaults` list determines the order in which configs are merged. `record.yaml` builds on the controller config this way:

```yaml
defaults:
  - controller                # merge conf/controller.yaml
  - _self_                    # then apply the keys defined inline below
```

`_self_` puts the inline keys *last*, so they override anything pulled in from groups.

## Command-line overrides

Anything in the composed config can be overridden on the command line, no quoting required for top-level keys:

```bash
solarian run-robot fps=60
solarian record num_episodes=5 episode_time_s=15
```

Deployment values are not part of the composed config, so change the relay address by editing `conf/deployment/<name>.yaml` or pointing at another deployment with `--deployment`.

Overrides also work for `+adding` keys not present in the base config:

```bash
solarian train +precision.amp_enabled=true
```

These are forwarded straight to Hydra's `compose(overrides=...)`.

## Picking a different config file

The `--conf` flag chooses the config directory and (optionally) the config name within it:

```bash
# Use a different conf directory
solarian run-robot --conf conf_experiment

# Use a different config name (conf/robot_v2.yaml) in the default directory
solarian run-robot --conf conf/robot_v2
```

To run the same configs against different hardware, reach for `--deployment` rather than a second `conf/` directory.

The CLI splits `dir/name` so the second form maps to `conf/robot_v2.yaml`.

## Custom command configs

A custom CLI command registered via `CommandRegistry.register_lazy(..., config_name="my_command")` automatically picks up `conf/my_command.yaml`. If the command's `get_config_class()` returns a Pydantic model, the loaded config is validated against it. See [CLI / Authoring a custom command](/docs/commands#authoring-a-custom-command).
