# Controllers

A **Controller** is the node that *decides* what the robot does. It receives [Observations](/docs/observations) from the relay server, computes the next [Action](/docs/actions), and sends it back. Anything that can produce an action — a teleoperator, a hard-coded script, a learned policy, an LLM-driven planner — is a controller. {{ className: 'lead' }}

Defined in [`solarian/core/controller.py`](https://github.com/solarian-dev/solarian/blob/main/solarian/core/controller.py).

There are two ways to produce that action. **Declaratively**, by starting [Skills](/docs/skills) and letting the base `control_step()` merge whatever they emit each tick — this is the usual path. Or **imperatively**, by overriding `control_step()` yourself, which is what the rest of this page shows.

## Defining a Controller

Subclass `Controller` and implement `control_step()`:

```python
from solarian.core import Controller
from solarian.core.action import ActionType
from myrobot.action import MyAction

class MyController(Controller):
    def control_step(self) -> MyAction:
        action = MyAction.zeros()
        action.action_type = ActionType.MODULE_ACTION
        # ... fill in action.arm.shoulder_pan.value, etc. ...
        return action
```

The framework calls `control_step()` at `cfg.fps` Hz. Whatever it returns is serialized and pushed to the relay server. An override that does not call `super().control_step()` replaces skill orchestration entirely, so nothing a running skill emits reaches the robot. It loses only skill orchestration — event dispatch and the observation snapshot happen in the loop *around* `control_step()`, so your `@event_handler` methods still run.

The latest observation is always available as `self.last_observation`, protected by `self.observation_lock` (Solarian's state-receiver thread overwrites it as new observations arrive).

```python
class MyController(Controller):
    def control_step(self) -> MyAction:
        with self.observation_lock:
            obs = self.last_observation
        action = MyAction.zeros()
        action.action_type = ActionType.MODULE_ACTION
        action.arm.shoulder_pan.value = obs.arm.shoulder_pan_pos.value + 0.01
        return action
```

## Registering your Controller class

Set `CONTROLLER_CLASS` in your project's [`settings.py`](/docs/settings):

```python
CONTROLLER_CLASS = 'myrobot.controller.MyController'
```

`solarian run-controller` reads this, imports the class, and instantiates it with the `ControllerConfig` parsed from `conf/controller.yaml`.

## Lifecycle

When `solarian run-controller` runs, the framework calls:

```text
Controller(cfg)            # __init__ — opens ZMQ sockets, builds shared memory
   │
   ├── connect()           # connect any controller-side modules (leader arms, etc.)
   ├── initialize()        # one-time setup hook
   └── start()             # spawn _state_receiver thread, control_loop thread,
                           # optional pynput keyboard listener, then on_start(),
                           # then display_loop() (or _headless_loop in headless mode)
```

The control loop is split into:

- **`_state_receiver`** (thread) — pulls every incoming `Observation` off the SUB socket and updates `self.last_observation` under a lock.
- **`control_loop`** (thread) — runs the tick below at `cfg.fps`, serializes the returned `Action`, and pushes it to the relay server.
- **`display_loop`** (main thread) — opens an OpenCV window per camera and renders the most recent observation. In `headless` mode this is replaced by a stdin loop.

## The tick

Every iteration of `control_loop` does the same three things in the same order:

```text
_drain_events()               # collect events from local modules, run @event_handlers
_tick_local_modules()         # tick inline modules, so they publish observations
control_step()                # decide — by default, merge what the skills emit
```

Draining first, on the control thread, is what makes input deterministic: handlers never run on a device callback thread, and every skill on the tick sees the same events and the same observations.

## Keyboard input

Keyboard is a [module](/docs/modules), not a special case in the controller. Every controller has one, and it turns key transitions into [events](/docs/events):

```python
from solarian.core.event import Event, EventType, event_handler

class MyController(Controller):
    STEP = 0.05

    @event_handler(EventType.KEY_DOWN)
    def on_key_down(self, event: Event):
        if event.data["key"] == 'a':
            self.target.arm.shoulder_pan.value -= self.STEP
        elif event.data["key"] == 'q':
            self.events["exit_early"] = True
```

Handlers fire **once per physical key transition** — OS auto-repeat is filtered out by the module — and run on the control thread when the controller drains, not on the pynput listener thread.

For *continuous* input, don't count key events; ask what is held right now:

```python
def control_step(self) -> MyAction:
    if 'w' in self.held_keys:
        self.target.arm.shoulder_pan.value += self.STEP
    self.target.action_type = ActionType.MODULE_ACTION
    return self.target
```

`held_keys` is state, so it is an observation, recomputed at drain time and stable for the whole tick.

<Note>
  If <code>pynput</code> isn't available (rare — it's pulled in by Solarian's base install), the global listener silently no-ops and the controller still works for non-keyboard inputs. A GUI window feeds the same module directly and needs no listener at all.
</Note>

Other input devices — a joystick, a SpaceMouse, a foot pedal — are modules too, emitting their own event types. Nothing in the controller has to change to accept one.

## Starting skills

A skill is something you construct and hand to `start_skill()`. Which key starts which skill is application policy, so it lives in your own `@event_handler` rather than in a framework-level binding table:

```python
class MyController(Controller):
    # Only a registry: what the think process may pick from, and what a
    # START_SKILL name resolves to.
    skills = (TeleopSkill, MoveSkill)

    def on_start(self):
        self._start_teleop()

    def _start_teleop(self):
        self.start_skill(TeleopSkill(arm=ARM, gripper=GRIPPER))

    @event_handler(EventType.KEY_DOWN)
    def start_bound_skill(self, event: Event):
        match event.data.get("key"):
            case "t":
                self._start_teleop()
            case "h":
                self.start_skill(MoveSkill(params={"pose": "home", "arm": "right_arm", "gripper": "right_gripper"}))
```

A key press only ever *starts*. `start_skill()` stops whatever already holds the modules the new skill commands, including an earlier instance of the same skill, so pressing `h` twice re-runs the move rather than leaving the arm with nothing driving it. `space` is the one key the framework claims, and it stops everything; nothing resumes on its own afterwards, so an operator who wants teleop back presses the key that starts it.

## Controller-side modules

A `Controller` can also attach hardware `Module` instances as class attributes. This is how leader-arm teleoperation works: the *controller* hardware (a small follower arm you wave around) is itself a Solarian module that streams positions, which the controller then turns into actions for the *real* robot.

```python
class TeleopController(Controller):
    leader = LeaderArmModule()      # controller-side module

    def control_step(self) -> MyAction:
        leader_pos = self.observations["leader"].latest()
        action = MyAction.zeros()
        action.action_type = ActionType.MODULE_ACTION
        for field, name in zip(action.arm.values(), leader_pos):
            field.value = float(leader_pos[name].value)
        return action
```

Read them from the module's [`ObservationBuffer`](/docs/glossary#observationbuffer) rather than calling `read_sensors()` yourself — a blocking serial read inside the control tick costs you the tick, and costs it once per reader. The buffer reads the hardware once, when `_tick_local_modules()` runs, and every reader after that is cheap.

`self.observations` is one mapping from module name to buffer covering both sides, so a controller-side leader arm and a robot-side follower are read the same way. See [Skills](/docs/skills) for what a skill does with it.

Controller-side modules read their config from `cfg.modules[name]` (i.e. inline under `controller.yaml` rather than from `conf/modules/<name>.yaml`).

## Lifecycle hooks you can override

<Properties>
  <Property name="initialize()">
    Runs once after <code>connect()</code>. Use for one-time setup that needs a live observation stream (homing, baseline reads, etc.).
  </Property>
  <Property name="on_start()">
    Runs after the receiver and control threads have started but before the display loop. Where an application brings up the skill it wants running from the start; the <code>AIController</code> uses it to start its <code>ThinkProcess</code>.
  </Property>
  <Property name="@event_handler(EventType.X)">
    Any number of methods, on any event type. Called on the control thread as the tick drains. See <a href="/docs/events">Events</a>.
  </Property>
  <Property name="control_step()">
    Compute and return the next <code>Action</code>. The base implementation merges what the running skills emit, so overriding it is optional.
  </Property>
</Properties>
